name: explain
description: >-
  Explain what code, changes, tasks, and systems are and how they work through evidence-backed walkthroughs and key source excerpts. Use when the
  requested outcome is understanding existing behavior, assumptions, design choices, or verification limits; not when the primary outcome is
  unresolved cause investigation, a new design recommendation, implementation, or formal approval.
---

## 역할
읽기 전용 설명 도구이며 phase가 아니다. 파일을 쓰지 않고 출력은 대화로만 나간다.
사용자가 코드를 다 읽지 않아도 후속 변경과 장애 대응을 판단할 수 있게 하는 것이 목적이다.
구현 수정·승인/거절·상태 전환은 이 skill의 역할이 아니며, `analyze`·`verify`를 자동으로 부르지 않는다.

실행 주체는 main이다.
여러 파일을 훑어 위치·존재·관례만 확인하면 되는 조사는 CLAUDE.md §agent·skill 라우팅에 따라 `Explore`에 맡기고, 설명 자체는 main이 쓴다.

`analyze`와의 경계 — 요청 산출물이 원인 규명이나 구조·대안 비교, 새 설계 제안이면 `analyze`다.
기존 코드·변경·시스템이 무엇이고 어떻게 작동하는지 이해시키는 것이 산출물이면 이 skill이다.
설명을 정확하게 만들기 위한 내부 조사와 분석은 이 skill 안에서 한다.

## 컨텍스트 로딩
1. `$ARGUMENTS`가 `features/<feature-dir>/` 또는 그 아래 파일과 매치하면 → feature mode.
   설명 범위를 이 feature로 한정하고, spec.md·design.md·implement.md 중 질문에 필요한 부분만 읽는다.
   문서에 적힌 설명은 현재 구현과 대조한 뒤에 쓴다.
2. `$ARGUMENTS`가 특정 파일·심볼·commit·diff를 가리키면 → 그 대상을 설명하고, 필요한 만큼 호출부·테스트·주변 맥락을 함께 읽는다.
3. `$ARGUMENTS`가 비어 있으면 다음과 같이 한다.
   - 활성 `features/<feature-dir>/` 범위가 있으면 (1)처럼 읽는다. 활성 범위의 뜻은 `implement` skill §컨텍스트 로딩과 같되,
     "implement 뜻"을 "설명 뜻"으로 읽는다.
   - 그 외에는 대화 맥락에서 대상을 잡고, 잡은 대상을 밝히고 진행한다.

결과를 바꾸는 모호함만 질문한다.
저장소·기능 문서·git 상태로 확인할 수 있는 범위와 사실은 먼저 조사한다.

## 근거 원칙
- 설명의 각 주장은 현재 코드·문서·diff·실행 결과 중 실제로 읽은 자리로 연결한다.
- 미커밋 변경을 포함해 테스트 실행 뒤 관련 코드가 바뀌었으면, 이전 결과를 현재 코드의 근거로 쓰지 않는다.
  같은 HEAD라는 것만으로 실행 당시와 현재 코드가 같다고 보지 않는다.
- 코드에 테스트가 있다는 것과 실제로 돌려서 통과했다는 것을 나눠 적는다.
  테스트를 근거로 쓸 때는 이름이나 통과 목록 대신 입력·조건·assertion·관찰 결과와 한계를 적는다.
- 새 실행은 설명의 중요한 불확실성을 줄이는 데 필요하고 현재 권한과 부작용 범위 안일 때만 한다.
- 확인한 사실 / 문서에 기록된 이유 / 근거에서 추론한 의도 / 검증되지 않은 가정을 나눠 적는다(CLAUDE.md §응답).
  당시 실제로 검토된 대안과 이번에 새로 제안하는 대안도 나눈다.

## 출력 구조
필수:
1. 결론 — 1-2 문장. 대상이 무엇을 하는지와 사용자에게 미치는 영향.
2. 흐름 — 대표 입력이나 시나리오를 따라, 경계에서 무엇이 들어와 어떤 결정과 변환을 거쳐 무엇이 나오는지 잇는다.
   파일별 diff 나열로 대신하지 않는다.
3. 근거 — 중요한 결정과 계약을 보여 주는 간결한 발췌와 `file:line`. 각 발췌가 무엇을 증명하는지 적는다.
4. 한계 — 확신 수준, 현재 테스트가 보장하는 범위, 확인하지 못한 것, 더 읽어야 할 위치와 그때 확인할 질문.

상황별 (대상에 실제로 해당할 때만 넣는다):
5. 계약과 불변 조건 — 보장하는 코드와 적용 범위, 위반 시 나는 장애까지 함께.
   보장 코드를 확인하지 못했으면 그 한계를 적는다.
6. 상태 전이 — 변경 전후 상태, 전이 조건, 저장 위치와 transaction 경계, 중간 실패 시 이미 반영된 상태와 남은 작업.
7. 외부 경계 — 실패나 응답 유실 뒤 성공 여부를 판단할 수 있는지, 재시도가 만드는 중복·불일치, 오류가 호출자와 후속 처리로 전파되는 방식.
8. 결함 — 확인된 결함은 영향과 근거를 앞세워 적는다.
   근거 있는 실패 가능성은 재현이 확인된 결함과 나누고, 각 반례를 현재 테스트가 다루는지 적는다.
9. 막힌 지점 — 사유를 적고 멈춘다. 세 가지다.
   - `target undefined`: 주어진 맥락과 저장소를 조사한 뒤에도 설명할 대상을 정할 수 없다.
   - `evidence unavailable`: 근거에 닿을 수 없어(파일 부재, 권한, 실행 불가) 설명의 핵심이 추정으로만 남는다.
     추정으로 채워 설명하지 않는다.
   - `needs input`: §컨텍스트 로딩이 남긴 질문처럼, 사용자 결정이나 외부 정보 없이는 설명이 성립하지 않는다.

   모든 막힌 지점은 다음을 담는다.
   - 근거: 무엇을 읽었고(파일·로그·문서) 무엇을 찾았는지.
   - 푸는 조건: 막힌 것을 푸는 구체적인 정보·결정·접근 권한.

   설명의 일부만 막혔으면 막힌 자리만 여기 적고 나머지는 그대로 설명한다.

흐름이나 책임 관계가 복잡할 때만 간결한 흐름도를 쓴다.
마지막에 가장 기억해야 할 동작·계약·위험을 짧게 남긴다.

## 대상별 관점
- 버그: 증상, 발생 조건, 원인, 잘못된 가정, 수정 전후 동작, 재현과 회귀 근거를 잇는다.
- 기능: 필요와 새 동작, 설계 선택과 영향을 설명한다.
- 기존 구조: 책임, 경계 계약, 데이터 흐름과 실패 방식을 설명한다.
- Milestone·기능 단위: 전체 시나리오를 중심으로 현재 가능한 동작, 그 근거, 남은 공백과 선행 조건을 설명한다.
  Task 설명을 이어 붙이거나 공식 완료를 선언하지 않는다.

## 지침
- 발췌는 설명 가치가 높은 자리를 고른다. 고정 개수나 분량 제한을 두지 않되 같은 원문을 반복해 덤프하지 않는다.
- 일반 점검 항목은 이 프로젝트의 코드·spec에서 확인한 것만 넣는다.
- 사용자가 설명을 문서로 남기라고 따로 요청하면 CLAUDE.md §문서화를 따른다.
  그 외에는 어떤 파일도 쓰지 않으며, Bash로도 파일을 고치지 않는다.
  같은 턴 안에서 다른 작업에 이어 불릴 수 있어 `disallowed-tools`를 걸지 않고 이 경계로만 막는다(`rules/claude-config-authoring.md`).
