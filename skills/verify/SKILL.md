---
name: verify
description: >-
  Judge whether the most recent implement Task (or a Per-Request change) satisfies its verification criteria, and whether any spec.md §5
  criteria completed by this Task actually hold. Returns approved/rejected with evidence.
---

## 역할
- 방금 구현한 Task가 목적과 검증 조건을 채웠는지, 이 Task로 끝나는 `SPEC §5.N`이 실제로 성립하는지 판단한다.
- 판정을 내기 전에는 Bash(`git stash`·`git checkout` 포함)로도 작업 트리의 파일을 고치거나 새로 만들지 않고, 커밋하지 않는다.

## 대상과 범위
- Phased mode 판정은 `implement` skill §컨텍스트 로딩과 같고, 대상은 직전 `implement`가 작업한 `[ ]` Task다(사용자가 `[x]` Task를 짚으면 재검증).
- Per-Request는 feature 문서를 읽지 않고, 아래의 Task 목적·검증 조건·완료 조건을 요청한 동작으로 읽는다.
- 검증할 변경은 main이 넘긴 변경 범위(비교할 커밋 범위나 고친 파일 목록)이고, 넘긴 게 없으면 커밋하지 않은 작업 트리다.
- 대상이나 범위가 하나로 정해지지 않으면 판정하지 않고 `- 판정 불가: 대상 | 범위 — <사유>` 한 줄만 낸다.

## 근거
- 이번에 직접 읽은 코드, 직접 돌린 명령, 출처를 `사용자 확인`으로 밝힌 사용자의 확인 결과만 근거로 쓰고, 이전 대화나 참조 필드는 근거가 아니다.
- 이번 변경에서 쓰거나 고친 테스트는 통과만으로 인정하지 않고, 검증 조건 `결과`가 말하는 대상마다 그 대상만 어기는 변경을 테스트가 잡는지 assertion과 대상 코드를 읽어 판단한다.
- 읽어서 판단할 수 없는 대상만 그 대상을 어기는 변형으로 테스트가 실패하는지 돌려 보고, 변형은 작업 트리 대신 사본이나 도구의 overlay에서 한다.
- 남아 있는 동작의 assertion을 약하게 하거나 경우를 지운 테스트는 `correctness`로 reject한다.
- Task 확인과 별개로 프로젝트 검증 명령(프로젝트 `CLAUDE.md`, 루트 `README.md` §검증 명령, CI 설정에 있는 것)의 build·typecheck·lint는 매번 돌린다.
- 테스트는 바뀐 코드와 바뀐 테스트가 닿는 범위만 돌리고(테스트 케이스만 바뀌었으면 그 테스트), 좁힐 수 없거나 이 Task로 모든 Task가 `[x]`가 되는 Phased Task면 전체를 돌린다.
- 직접 볼 수 없는 확인은 이 머신에서 외부 쓰기 없이 돌릴 수 있는 대안 환경(Docker, dev API 읽기 호출, 사본 실행 등)으로 먼저 본다.
- 대안 환경으로도 사람만 볼 수 있는 것(화면 모양, 실기기, 운영 DB 등)은 `미확인`으로 적고 그것만으로 reject하지 않는다.
- 파일이 바뀌었는지는 `git status`·`git diff`로 본다.
- 이번 변경과 무관한 실패는 reject 사유가 아니라 근거와 함께 남길 항목이다.

## 판단 기준
1. Task 목적이 말하는 동작이 실제로 되는가(검증 조건 통과로 대신하지 않는다).
2. 검증 조건을 채우는가.
3. spec.md의 완료 조건·제약·제외 범위와 design.md의 지켜야 할 결정을 지키는가.
   Per-Request는 `docs/design.md`가 있으면 그 책임 경계·의존 방향·불변 조건을 지키는가.
4. Phased에서는 이 Task를 `[x]`로 바꾸면 매핑 Task가 모두 `[x]`가 되는 `SPEC §5.N`마다, 매핑 Task들의 변경을 합쳐 그 조건이 성립하는지 본다.
   - `성립` / `불성립`(→ `correctness`) / `미확인` 중 하나로 적는다.
   - 성립하지 않는 문장이 매핑 Task의 목적·검증 조건에 없으면 코드 문제가 아니므로 reject하지 않고 `매핑 누락`으로 적는다.
5. 변경이 기존 모듈 경계와 의존 방향을 지키는가.

## verifier 위임 기준
- main은 Phased를 verifier agent에 맡기고, Per-Request는 사용자가 독립 검증을 원할 때만 맡긴다.
- 위임 프롬프트에는 `<feature-dir>`, 대상 Task나 요청, 재검증인지, 변경 범위, 직전 `implement`의 비고·접근 이탈·실행한 검증, 실행하면 안 되는 외부 부작용(운영 호출, dev 쓰기 등), 사용자의 확인 결과, 사용자가 직접 한 판정 방법(빌드·테스트·변형 여부, reject 기준) 변경 지시의 인용만 적는다.

## 출력 구조
```markdown
1. 판정: `approved` | `rejected`
2. 대상: task-<nnn>: <제목> | <요청 인용>
3. 완료되는 요구사항
   - SPEC §5.<N>: `성립` | `불성립` | `미확인` | `매핑 누락` — <근거>
4. 문제
   - 분류: `correctness` | `design/scope` | `evidence`
   - 수정 소유 단계: `implement` | `implement-init` | `design-init` | `spec-init`
   - <문제와 근거>
5. 근거 — <확인한 기준마다 관찰한 동작, 테스트 결과, `미확인` 항목과 사람만 볼 수 있는 이유, 판정 방법 변경>
6. 설명 — <무엇이 어떻게 바뀌었는지, 남은 지적>
```
- 3번은 Phased에서만, 4번은 `rejected`일 때만 쓰고, 6번은 `rejected`면 남은 지적만 쓴다.
- 문제와 남은 지적은 찾은 것을 한 번에 모두 적고, 문제마다 같은 원인이 있는 다른 위치도 함께 적되 범위 밖 위치는 남은 지적에 둔다.
- 분류가 `evidence`면 `수정 소유 단계` 대신 `- 해소 조건: <다시 검증하려면 필요한 입력·환경>`을 쓴다.
- 문제가 여럿이면 분류는 `design/scope` > `correctness` > `evidence`, 수정 소유 단계는 가장 앞선 단계 하나를 쓴다.

## reject 분류
- `correctness`: 다음 중 하나다.
  - 목적·검증 조건·완료 조건을 어기는 입력이나 상태가 있다.
  - `확인`이 테스트인 Phased Task에서 `결과`가 말하는 대상 중 그것을 어기게 코드를 바꿔도 테스트가 모두 통과하는 것이 있다.
  - 변경 범위 안에 버그가 있다.
  - 공개 식별자의 주석이 반환값·에러·nil·동시성 같은 계약을 코드와 다르게 말해, 주석대로 호출하면 틀린 동작이 난다.
- `design/scope`: design.md의 지켜야 할 결정이나 기존 모듈 경계를 벗어나거나 요청 범위를 넘어, 구현과 design.md 중 무엇을 고칠지 정해야 한다.
- `evidence`: `미확인`이 아닌데 근거를 모으지 못해 판단하지 못했다.
- `남은 지적`에는 관례나 `rules/code-common.md` 위반, 쓰이지 않는 추상화·중복, 계약을 바꾸지 않는 주석 표현, 타입으로 막을 수 있었지만 실제로 생기지 않는 잘못된 상태처럼 동작이 맞는 문제만 둔다.

## verify 후처리
main이 하는 일이며, Per-Request는 rejected의 마지막 항목만 따른다.
- approved
  - `매핑 누락`이 있으면 그 문장을 맡는 Task의 참조에 `SPEC §5.N`을 더한다.
  - 맡을 Task가 없으면 아래 단계는 하지 않고 사용자에게 `commands/implement-init.md` §매핑의 세 선택지를 묻는다.
  - 체크박스를 `[x]`로 바꾸고, 접근 이탈이 있었으면 접근 필드와 달라진 design.md 기본안 서술을 실제 구현대로 고친다.
  - `진행`·`최근 reject` 줄을 지우고 `- 승인 근거: <yyyy-MM-dd> — 실행: <명령과 결과>; 미확인: <사람만 볼 수 있어 못 본 항목>; 판정 방법 변경: <사용자 지시 인용>`을 참조 아래에 쓴다(`미확인`·`판정 방법 변경`은 있을 때만).
  - 모든 Task가 `[x]`이고 `미확인`이 남은 Task가 없으면 README를 `[x] IMPLEMENT`로 바꾸고 작업 히스토리에 `- <yyyy-MM-dd>: IMPLEMENT 완료`를 더하고, 낡은 프로젝트 루트 문서는 갱신 후보로만 알린다.
  - 지운 `진행` 줄에 있던 파일과 feature 문서를 `commit-push` skill §절차 3·4대로 현재 브랜치의 한 커밋에 싣고(push하지 않는다), 접근 이탈의 이유와 버린 대안은 커밋 본문에 쓴다.
- 사용자 확인
  - 사용자가 `미확인` 항목의 확인 결과를 알려 주면, 결과가 기대대로면 그 항목을 `승인 근거`에서 지우고 `사용자 확인: <결과>`를 더한 뒤 위 README 단계를 다시 보고, 고친 feature 문서를 한 커밋에 싣는다.
  - 결과가 기대와 다르면 그 Task를 재검증 대상으로 `verify`를 부른다.
- rejected
  - 참조 아래에 `- 최근 reject: <분류> — <문제 한 줄, evidence면 해소 조건>`을 쓰거나 고치고 체크박스는 `[ ]`로 둔다.
  - 이미 `[x]`였던 Task면 `[ ]`로 되돌리고 `승인 근거`를 지우며, README가 `[x] IMPLEMENT`였으면 되돌리고 히스토리에 적는다.
  - 문제를 사용자에게 전하고, `/implement-loop`가 아니면 다시 구현하지 않고 사용자 판단을 기다린다.
