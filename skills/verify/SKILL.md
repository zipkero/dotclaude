---
name: verify
description: >-
  Judge whether the most recent implement Task (or a Per-Request change) satisfies its verification criteria, and whether any spec.md §5
  criteria completed by this Task actually hold. Returns approved/rejected with evidence.
---

## 역할
- 방금 구현한 Task가 목적과 검증 조건을 채웠는지, 이 Task로 끝나는 `SPEC §5.N`이 실제로 성립하는지 판단한다.
- 판정 중에는 Bash로도 작업 트리를 바꾸거나 커밋하지 않고(`.evidence/` 기록은 뺀다), 변형·실험은 작업 트리 밖 사본이나 도구의 overlay에서 한다.

## 대상과 범위
- Phased mode 판정은 `~/.claude/skills/implement/SKILL.md` §컨텍스트 로딩과 같고, 대상은 직전 `implement`가 작업한 `[ ]` Task이며, 사용자가 `[x]` Task를 짚으면 그 Task다.
- 재검증(reject 뒤 재작업이나 `[x]` Task를 다시 보는 판정)은 직전 문제가 원인째 고쳐졌는지와 재작업이 바꾼 부분을 본다.
- Per-Request는 feature 문서를 읽지 않고, 아래의 Task 목적·검증 조건·완료 조건을 요청한 동작으로 읽는다.
- 검증할 변경은 main이 넘긴 변경 범위(커밋 범위나 파일 목록)이고, 넘긴 게 없으면 커밋하지 않은 작업 트리이며, 그 내용은 보고가 아니라 `git diff`로 직접 본다.
- 대상이나 범위가 하나로 정해지지 않으면 판정하지 않고 `- 판정 불가: 대상 | 범위 — <사유>` 한 줄만 낸다.

## 근거
- 이번에 직접 읽은 코드, 직접 돌린 명령, `사용자 확인`으로 출처를 밝힌 사용자의 확인 결과만 근거로 쓴다.
- 실행 결과의 수치와 판정 문구는 출력 줄을 그대로 인용한다.
- 외부 시스템 호출의 허용 범위와 응답 저장은 `~/.claude/skills/implement/SKILL.md` §코드와 테스트를 따르고, 근거에 `.evidence/` 경로와 판정에 쓴 출력 줄을 인용한다.
- 프로젝트 검증 명령(출처는 `~/.claude/skills/implement/SKILL.md` §코드와 테스트)의 build·typecheck·lint를 직접 돌린다.
- 테스트는 바뀐 코드와 테스트가 닿는 범위만 돌리고, 좁힐 수 없거나 이 Task로 모든 Task가 `[x]`가 되면 전체를 돌린다.
- 이번 변경에서 쓰거나 고친 테스트는 통과만으로 인정하지 않고, `결과`가 말하는 대상마다 그 대상만 어기는 변경을 잡는지 assertion과 대상 코드를 읽어 판단하고, 읽어서 판단할 수 없을 때만 그 대상을 어기는 변형을 돌려 본다.
- 직접 볼 수 없는 확인은 이 머신에서 프로젝트 `CLAUDE.md` §검증 환경이 허용한 범위(없으면 외부 쓰기 없이)로 돌릴 수 있는 대안 환경(Docker, dev API 읽기 호출, 사본 실행 등)으로 보고, 검증 조건의 확인 수단을 바꿨으면 `대체: <조건의 수단> → <쓴 수단> — <뜻이 유지되는 근거>`를 적는다.
- 대안 환경으로도 사람만 볼 수 있는 것(화면 모양, 실기기, 운영 DB 등)은 `미확인`으로 적고, 그것만으로 reject하지 않는다.
- 실패는 바꾸기 전 코드의 사본에서 같은 명령으로 같은 실패를 확인했을 때만 이번 변경과 무관하다고 보고 근거에 남긴다.

## 판단 기준
1. 검증 조건과 별개로, Task 목적이 말하는 동작이 실제로 되는가.
2. 검증 조건을 채우는가.
3. spec.md의 완료 조건·제약·제외 범위, design.md의 지켜야 할 결정(Per-Request는 `docs/design.md`의 책임 경계·의존 방향·불변 조건), 기존 모듈 경계와 의존 방향을 지키는가.
4. Phased에서는 이 Task를 `[x]`로 바꾸면 매핑 Task가 모두 `[x]`가 되는 `SPEC §5.N`마다, 매핑 Task들의 변경을 합쳐 그 조건이 성립하는지 본다.
   - `성립` / `불성립`(→ `correctness`) / `미확인` 중 하나로 적는다.
   - 성립하지 않는 문장이 매핑 Task의 목적·검증 조건에 없으면 코드 문제가 아니므로 reject하지 않고 `매핑 누락`으로 적는다.

## verifier 위임 기준
- main은 Phased를 verifier agent에 맡기고, Per-Request는 사용자가 독립 검증을 원할 때만 맡긴다.
- 위임 프롬프트에는 `<feature-dir>`, 대상 Task나 요청, 변경 범위, 재검증이면 직전 문제와 남은 지적, 직전 `implement`의 비고·접근 이탈·실행한 검증, 실행하면 안 되는 외부 부작용(운영 호출, dev 쓰기 등), 사용자의 확인 결과와 사용자가 직접 한 판정 방법(빌드·테스트·변형 여부, reject 기준) 변경 지시의 인용만 적는다.

## 출력 구조
```markdown
1. 판정: `approved` | `rejected`
2. 대상: task-<nnn>: <제목> | <요청 인용>
3. 완료되는 요구사항
   - SPEC §5.<N>: `성립` | `불성립` | `미확인` | `매핑 누락` — <근거>
4. 문제
   - 분류: `correctness` | `design/scope` | `evidence`
   - 수정 소유 단계: `implement` | `implement-init` | `design-init` | `spec-init`
   - <문제와 근거>
5. 근거 — <기준마다 관찰한 동작, 돌린 명령과 결과, 변형과 결과, `미확인` 항목과 사람만 볼 수 있는 이유, 대체, 판정 방법 변경>
6. 설명 — <무엇이 어떻게 바뀌었는지, 남은 지적>
```
- 3번은 Phased에서만, 4번은 `rejected`일 때만 쓰고, 6번은 `rejected`면 남은 지적만 쓴다.
- 문제와 남은 지적은 찾은 것을 한 번에 모두 적고, 문제마다 같은 원인이 있는 다른 위치와 입력도 함께 적되 범위 밖 위치는 남은 지적에 둔다.
- 분류가 `evidence`면 `수정 소유 단계` 대신 `- 해소 조건: <다시 검증하려면 필요한 입력·환경>`을 쓴다.
- 문제가 여럿이면 분류는 `design/scope` > `correctness` > `evidence`, 수정 소유 단계는 가장 앞선 단계 하나를 쓴다.

## reject 분류
- `correctness`: 다음 중 하나다.
  - 실제로 생길 수 있는 입력·상태에서 목적·검증 조건·완료 조건이 깨지고, 그 근거를 적을 수 있다.
  - `확인`이 테스트인 Phased Task에서 `결과`가 말하는 대상 중 그것을 어기게 코드를 바꿔도 테스트가 모두 통과하는 것이 있다.
  - 공개 식별자의 주석이 반환값·에러·nil·동시성 같은 계약을 코드와 다르게 말해, 그 식별자를 부르는 코드가 틀리게 동작한다.
  - 이번 변경이 남아 있는 동작을 검사하던 테스트의 assertion을 약하게 하거나 경우를 지웠다.
- `design/scope`: design.md의 지켜야 할 결정이나 기존 모듈 경계를 벗어나거나 요청 범위를 넘어, 구현과 design.md 중 무엇을 고칠지 정해야 한다.
- `evidence`: `미확인`이 아닌데 근거를 모으지 못해 판단하지 못했다.
- 위에 들지 않는 지적(관례 위반, 주석·문서 표현, 생길 근거가 없는 입력 등)은 `남은 지적`에 둔다.

## verify 후처리
main이 하는 일이며, Per-Request는 rejected의 마지막 항목만 따른다.
- approved
  - `매핑 누락`이 있으면 그 문장을 맡는 Task의 참조에 `SPEC §5.N`을 더하고, 맡을 Task가 없으면 `미확인`으로 남긴다.
  - 근거에 `대체`가 있으면 그 Task의 `결과`·`확인`을 쓴 수단대로 고치는 검증 조건 수정으로 보아 `rules/feature-docs.md` 기준대로 처리하고, 사용자에게 물어야 하면 고치지 않고 `미확인`으로 남긴다.
  - 체크박스를 `[x]`로 바꾸고, 접근 이탈이 있었으면 접근 필드와 달라진 design.md 기본안 서술을 실제 구현대로 고친다.
  - `진행`·`최근 reject` 줄을 지우고 참조 아래에 `- 승인 근거: <yyyy-MM-dd> — 실행: <명령> → <결과>; 외부: <.evidence 경로> → <인용>; 변이: <변형> → <결과>; 미확인: <사용자가 확인하거나 정해야 하는 항목>; 판정 방법 변경: <사용자 지시 인용>`을 쓰거나 고친다(`실행` 외에는 있을 때만).
  - 모든 Task가 `[x]`이고 implement.md에서 `미확인:`이 검색되지 않으면 README를 `[x] IMPLEMENT`로 바꾸고 작업 히스토리에 `- <yyyy-MM-dd>: IMPLEMENT 완료`를 더하고, 낡은 프로젝트 루트 문서는 갱신 후보로만 알린다.
  - 지운 `진행` 줄의 파일과 feature 문서를 `commit-push` skill §절차 3·4대로 현재 브랜치의 한 커밋에 싣고(push하지 않는다), 접근 이탈의 이유와 버린 대안은 커밋 본문에 쓴다.
- 사용자 확인
  - `미확인` 항목을 사용자에게 묻되, 매핑 누락은 `commands/implement-init.md` §매핑의 세 선택지로, `대체`는 바꾼 수단을 받아들일지로 묻는다.
  - 답을 받으면 그 항목을 `승인 근거`에서 지우고 답대로 반영한 뒤(확인 결과는 `사용자 확인: <결과>`, 받아들인 `대체`는 `검증 조건 변경`) 위 README 단계를 다시 보고, 고친 feature 문서를 한 커밋에 싣는다.
  - 확인 결과가 기대와 다르거나 `대체`를 받아들이지 않으면 반영하지 않고 그 Task를 재검증 대상으로 `verify`를 부른다.
- rejected
  - 참조 아래에 `- 최근 reject: <분류> — <문제 한 줄, evidence면 해소 조건>`을 쓰거나 고치고 체크박스는 `[ ]`로 둔다.
  - 이미 `[x]`였던 Task면 `[ ]`로 되돌리고 `승인 근거`를 지우며, README가 `[x] IMPLEMENT`였으면 되돌리고 히스토리에 적는다.
  - 문제를 사용자에게 전하고, `/implement-loop`가 아니면 다시 구현하지 않고 사용자 판단을 기다린다.
