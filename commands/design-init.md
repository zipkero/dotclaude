`features/<feature-dir>/design.md`를 쓴다.

Feature directory: $ARGUMENTS

## 실행 주체
- analyzer agent가 design.md를 쓴다(`agents/analyzer.md` §하는 일).
- main은 맡기기 전에 §덮어쓰기 확인을 받는다.
- 다 쓰면 main이 읽고 검토한 뒤 §README 갱신을 한다.

main 검토:
- spec.md §5의 모든 조건이 본문에 `SPEC §5.N`으로 연결돼 있는지 본다.
- 표기만 빠졌으면 main이 넣는다.
- 설계가 그 조건을 다루지 않으면 analyzer에 다시 맡긴다.
- 조건이 feature 범위 밖으로 보이면 사용자에게 묻는다.

## 역할
- spec.md에서 나온 설계 결정을 모두 담는다.
- `/clear` 후 새 세션에서도 spec.md와 design.md만으로 implement.md를 만들 수 있게 쓴다.
- spec.md §5 내용은 옮기지 않고 `SPEC §5.N`으로 가리킨다.
  설계가 그 조건에 어떻게 기여하는지는 글로 적는다.
- README의 `[x] DESIGN`은 design.md가 지금 spec.md 기준으로 쓰였다는 뜻이다.

## 전제 조건
- spec.md가 없으면 멈추고 `/spec-init`을 안내한다.
- spec.md를 전부 읽는다.
- §1 범위를 넘거나, 요구사항을 더하거나, 약하게 바꾸지 않는다.
- §1 입력 맥락이 있으면 거기서부터 코드를 조사한다.
- analyzer는 아래 경우 design.md를 쓰지 않고 main에 돌려준다.
  - spec.md 승인 전 확인에 `(보류)`가 아닌 항목이 남아 있다.
    main이 사용자에게 묻고, 요구사항이 바뀌면 spec.md를 고친 뒤 다시 맡긴다.
  - spec.md 안에 설계에 영향을 주는 모순이 있다.
  - 고르는 쪽에 따라 외부 계약, 저장 형식·데이터 모델, 외부 연동, 사용자가 보는 결과가 달라지는데 spec.md로 정할 수 없는 결정이 있다.
    main이 사용자에게 묻는다.

## 덮어쓰기
- design.md가 이미 있으면 묻는다.
- implement.md가 있으면 영향받는 Task의 승인이 취소된다는 것도 알린다.

## design.md 구조
아래 섹션만 둔다.
`<…>`는 채울 자리다.

```markdown
# <feature-name> 설계

## 승인 전 확인
- <채택안이 의도와 맞는지 묻는 질문>. 관련 본문: §N

## 근거
<실제로 읽은 spec.md 범위와 코드에서 확인한 사실. 추정은 섞지 않는다>

## 1. 구조
<모듈·컴포넌트·레이어를 어떻게 나누는지. 파일이 아니라 경계 단위로 쓰고, 경계가 분명하지 않을 때만 타입·인터페이스 이름을 적는다>

## 2. 데이터 흐름
<진입점부터 결과까지의 흐름, 상태 변화, 외부 연동 지점, 실패 경로. 경계나 상태가 여럿이면 Mermaid 다이어그램도 쓴다>

## 3. 인터페이스
<경계를 넘는 API 시그니처, 이벤트 형태, 이웃 모듈과의 약속>

## 4. 영향 범위
<건드리는 기존 모듈·저장소와 그 의존. 하위 호환·마이그레이션은 기존 호출자·데이터가 실제로 깨질 때만. 없으면 "해당 없음">

## 5. Decision Points
**<판단이 갈린 지점>**
- <옵션>: <얻는 것>. <치르는 대가>.
- <옵션>: <얻는 것>. <치르는 대가>.
- 채택: <고른 옵션>. <이유>.
```

- 승인 전 확인은 채택안이 의도와 맞는지 사용자 판단이 필요할 때만 둔다.
  본문 결정을 다시 여는 용도로 쓰지 않는다.
  - 답을 받으면 본문에 반영하고 항목을 지운다.
  - 사용자가 보류하면 `- (보류) <질문>. 관련 본문: §N`으로 남긴다.
- §5에는 실제로 판단이 필요했던 설계 선택과 설계를 막는 위험을, 검토한 옵션과 함께 적는다.
  정확성에 영향을 주는 실행 순서, 추상화·확장 포인트 도입도 여기에 들어간다.
  없으면 "해당 없음"으로 쓴다.
- §5에서 정하지 않은 추상화는 만들지 않고 직접 구현하는 것이 기본이다.
- 사용자가 보류한 결정만 `채택: 미정`과 보류 이유로 남긴다.
- 구현 체크리스트, Task 순서, 세부 코딩 내용, 근거 없는 일반론은 넣지 않는다.

## README 갱신
- `[ ] DESIGN`을 `[x] DESIGN`으로 바꾸고 작업 히스토리에 `- <yyyy-MM-dd>: DESIGN 작성`을 더한다.
- 재작성이면 `rules/feature-docs.md` §재작성 시 승인 취소를 따른다.
