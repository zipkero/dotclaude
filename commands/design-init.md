---
description: Create design.md (design decisions) under features/<feature-dir>/ from spec.md
argument-hint: "<feature-dir>"
---

> 사용 시점: `/spec-init` 이후, `/implement-init` 이전. `/implement-init`이 소비할 설계 기준을 만든다.

`features/<feature-dir>/design.md`를 작성한다.
DESIGN은 feature를 어떻게 구조화하고 어떤 설계 선택을 확정했는지를 잡는다.

Feature directory: $ARGUMENTS

## 실행 주체
analyzer agent가 아래 구조대로 design.md를 작성하고 직접 기록한다(기록 계약은 `agents/analyzer.md` §산출물 기록 의무).
main은 위임 전에 §덮어쓰기 규칙의 확인을 받고, 기록된 파일을 읽어 검토한 뒤 §README 갱신을 한다.

main 검토:
- spec.md §5의 모든 조건이 본문에 `SPEC §5.N`으로 걸려 있는지 본다.
  설계에 반영됐는데 표기만 빠졌으면 main이 더하고, 설계가 그 조건을 다루지 않으면 analyzer에 다시 맡기며, feature 범위 밖으로 보이면 design.md에 적지 않고 사용자에게 묻는다.
- 미해결 결정 중 선택에 따라 외부 계약 형태, 저장 형식·데이터 모델, 외부 연동의 뜻, `SPEC §5.N`의 사용자 관찰 결과가 달라지는 것은 사용자에게 묻는다(CLAUDE.md §요청 해석).
- 받은 답은 요구사항이 바뀌는 경우를 포함해 `rules/feature-docs.md`대로 반영한다.

## 역할
- spec.md에서 도출한 설계 기준이며 모든 구조·설계 결정을 담는다.
  implement.md에는 결정을 남기지 않는다.
- feature README 상태판의 `[x] DESIGN`은 design.md가 현재 승인된 spec.md 기준으로 작성되었다는 뜻이다.
- 새 세션(`/clear` 이후)에서도 spec.md + design.md만으로 implement.md를 만들 수 있게 쓴다.
- spec.md §5 본문은 옮기지 않고 `SPEC §5.N`으로 가리키며, 결정이 그 동작에 어떻게 기여하는지는 평문으로 적는다.

## 전제 조건
- feature directory가 비어 있으면 중단하고 `/design-init 20260506-001-payment-integration`처럼 인자를 달라고 안내한다.
- spec.md가 없으면 중단하고 `/spec-init`을 먼저 실행하도록 안내한다.
- spec.md 전체를 읽고, §1 범위를 넘거나 요구사항을 더하거나 약하게 바꾸지 않는다.
  §1 입력 맥락이 있으면 코드베이스 조사의 출발점으로 삼는다.
- analyzer는 다음이면 design.md를 기록하지 않고 main에 돌려준다.
  - spec.md 승인 전 확인에 `(보류)`가 아닌 항목이 남아 있다.
    main이 사용자에게 묻고, 답으로 요구사항이 바뀌면 `rules/feature-docs.md`대로 spec.md를 고친 뒤 진행한다.
  - spec.md 안의 모순이 설계 결정에 영향을 준다.

## 덮어쓰기 규칙
- design.md가 이미 있으면 확인받고, implement.md가 있으면 무효화될 수 있으며 이후 영향받은 섹션을 갱신해야 한다는 것을 함께 알린다.

## design.md 구조
`<…>`는 채울 자리이며, 아래 섹션 밖의 섹션과 체크박스는 두지 않는다.

```markdown
<!-- prowl-workflow: v1 -->
# <feature-name> 설계

## 승인 전 확인
- <채택안이 의도와 맞는지 확인하는 판단 질문>. 관련 본문: §N

## 근거
<실제로 읽은 spec.md 범위와 코드베이스에서 확인한 사실(기존 경계·타입·삭제 여부, 의존 탐색 흔적). 추정과 섞지 않는다>

## 1. 구조
<모듈·컴포넌트·레이어 배치와 나누는 방식. 파일이 아니라 경계 중심이며, 경계가 자명하지 않을 때만 타입·인터페이스 이름>

## 2. 데이터 흐름
<진입점부터 응답 반환까지 거치는 모듈 순서, 상태의 변경 트리거·전이 조건·도달 가능한 상태, 외부 통합 지점, 에러·실패 경로, 동시성 분기. 여러 경계나 상태가 있으면 글이나 Mermaid 다이어그램>

## 3. 인터페이스
<경계를 가로지르는 API signature, event 형태, 인접 모듈과의 계약>

## 4. 영향 범위
<실제로 건드리는 기존 모듈·파일·DB 테이블과 그 직접·간접 의존. 하위 호환·마이그레이션은 기존 호출자·저장 데이터·외부 계약이 실제로 깨질 때만. 없으면 "해당 없음">

## 5. Decision Points
**<판단이 갈린 지점>**
- <옵션>: <이 옵션이 주는 것>. <이 옵션의 대가>.
- <옵션>: <이 옵션이 주는 것>. <이 옵션의 대가>.
- 채택: <고른 옵션>. <근거>.
```

- 승인 전 확인은 그 feature에서 무엇이 걸려 있는지 드러나는 질문이 있을 때만 두며, 본문 결정을 다시 여는 질문으로 쓰지 않는다.
  답을 받으면 `rules/feature-docs.md`대로 §1–§5에 반영하고 항목을 지우며, 사용자가 보류한 항목은 `- (보류) <판단 질문>. 관련 본문: §N`으로 남긴다.
  남아 있는 항목은 답을 받지 않은 질문이며 이후 단계가 이 표기로 판정한다.
- §5에는 판단이 필요했던 설계 선택(구조, 데이터·상태 모델, 여럿 가능한 인터페이스 형태, 정확성에 영향을 주는 실행 순서, 직접 구현 vs 추상화·확장 포인트)과 설계를 막는 위험을 옵션과 함께 둔다.
  옵션 수는 실제 검토한 만큼이고, 판단할 거리가 없으면 "해당 없음"이다.
  §5에서 확정하지 않은 추상화 지점은 직접 구현이 기본값이다.
- §실행 주체의 미해결 결정 중 사용자가 보류한 것만 `채택: 미정`과 보류 사유로 둔다(`commands/implement-init.md` §전제 조건의 미해결 판정 대상).
- 구현 체크리스트·Task 순서, 저수준 코딩 디테일, spec.md·코드·사용자 입력에 근거 없는 일반 체크리스트·가정·호환성 우려는 두지 않는다.

## README 갱신
- 상태 `[ ] DESIGN`을 `[x] DESIGN`으로 바꾸고 작업 히스토리에 `- <yyyy-MM-dd>: DESIGN 작성`을 더한다.
- 재작성이면 `rules/feature-docs.md` §재작성 시 하위 승인 상태 초기화를 따른다.
