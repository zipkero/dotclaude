> 사용 시점: 프로젝트 최초 문서화 단계. Phased 흐름보다 앞서며, ROADMAP의 마일스톤별 feature 후보가 `/spec-init`의 입력이 된다.

프로젝트 루트 `README.md`와 `ROADMAP.md`를 작성한다. README는 프로젝트의 정체성·목적·현재 사용 방법·문서 진입점을 소유하고, ROADMAP은 최종 결과물·서비스 완료 기준·포함 범위·마일스톤·최종 관문·보류 범위를 소유한다. feature별 문서(`spec.md`·`analysis.md`·`implement.md`)는 만들지 않는다.

프로젝트 이름 또는 한 줄 설명: $ARGUMENTS

## 역할
- 다음 세션에서 이전 대화 없이 읽어도 프로젝트 목표와 현재 기준을 복원할 수 있는 기준 문서다.
- 정적 문서이며 진행 상황을 추적하는 문서가 아니다. Task 단위 진행 상태는 feature `README.md`와 `implement.md`가 소유한다.
- 최종 결과물과 마일스톤별 실행 범위를 분리한다. 초기에 구현 가능한 범위를 최종 목표로 축소해 쓰지 않는다.

## 전제 조건
- 이 command를 쓰는 경우는 새 프로젝트의 최초 문서 생성, 또는 루트 `README.md`·`ROADMAP.md` 초기 작성이다.
- 기능 추가, 공개 contract 변경, 여러 Task로 나눠야 하는 구현 작업은 `/spec-init`부터 시작한다.
- 이미 `ROADMAP.md`가 있고 특정 feature만 구체화하려는 요청이면 문서를 쓰지 않고 `/spec-init`이 필요하다고 보고한다.
- README 문구만 고치는 작고 명확한 변경은 이 command 없이 Per-Request로 처리한다.
- 작성 전에 기존 `README.md`·`ROADMAP.md`, 주요 manifest, 기존 문서, 코드 구조를 확인한다.
- 인자가 비어 있으면 프로젝트 이름은 저장소·manifest에서 확인한 값을 쓰고, 확인되지 않으면 질문한다.
- 최종 결과물, 핵심 사용자, 목표 제공 수준, 서비스 완료 기준, 포함 범위, 보류 범위의 해석 차이가 결과를 바꾸면 문서 작성 전에 질문으로 정리한다(방식은 CLAUDE.md §요청 해석).
- 미확정 판단이 남아 있으면 추정으로 채워 문서를 생성하지 않는다.

## 산출 경로
- 프로젝트 루트 `README.md`
- 프로젝트 루트 `ROADMAP.md`
- `features/<feature-dir>/`는 만들지 않는다. 그 경로 규칙은 `commands/spec-init.md` §산출 경로가 소유한다.

## 덮어쓰기 규칙
- 두 문서 중 일부가 이미 있으면 의미 있는 기존 구조를 보존하고 필요한 섹션만 쓴다.
- 기존 `README.md`·`ROADMAP.md`나 feature 문서의 기준을 바꾸는 갱신은 영향 범위를 먼저 보고하고 사용자 확인을 받은 뒤 진행한다.

## 작성 규칙
- 기술 선택, 명령어, 현재 동작은 확인한 파일이나 실행 결과에 근거해서만 단정한다.
- 확인되지 않은 설치 방법, 실행 명령, 지원 기능, 성능 목표, 운영 보장은 추정으로 쓰지 않는다.
- 마일스톤은 이 단계에서 완성되는 검증 가능한 결과, 의존 관계, 전환 기준만 정의한다. feature별 상세 완료 조건과 검증 기준은 `/spec-init` 이후에서 확정한다.
- 최종 관문은 목표 제공 수준에 별도 관문이 필요한 경우에만 쓰고, 근거 없는 운영 환경 요구사항을 관례적으로 추가하지 않는다.
- feature 문서 후보는 kebab-case 이름으로만 제시하고, `features/<feature-dir>/` 경로를 확정하거나 디렉토리를 만들지 않는다.
- 보류·제외 범위는 사용자가 언급했거나 최종 결과물과 직접 경계를 이루는 항목만 적는다.

## README.md 구조
프로젝트 성격에 맞게 간결하게 다음을 둔다.

- 프로젝트 이름과 한 줄 설명
- 해결하려는 문제와 대상 사용자
- 현재 상태
- 확인된 설치·실행·사용 방법
- 주요 문서 링크
- 라이선스나 운영상 주의가 확인된 경우 그 정보

세부 요구사항, 마일스톤 계획, 보류 항목의 판단 근거는 `ROADMAP.md`에 둔다.

```markdown
# <프로젝트명>

## 개요

## 현재 상태

## 사용 방법

## 문서
- [ROADMAP.md](./ROADMAP.md)
```

## ROADMAP.md 구조
- 최종 결과물: 사용자가 기대하는 완성 상태, 핵심 사용자 가치와 목표 제공 수준
- 서비스 완료 기준: 대상 사용자가 최종 결과를 얻을 수 있음을 확인하는 관찰 가능한 조건
- 포함 범위: 최종 결과물에 포함되는 주요 기능
- 마일스톤: 이 단계에서 완성되는 검증 가능한 결과, 의존 관계, 전환 기준과 feature 문서 후보 이름
- 최종 관문: 필요한 경우 여러 마일스톤에 공통으로 적용되는 품질·배포·운영 조건
- 보류·제외 범위: 제외 이유, 관련 위험과 다시 검토할 조건

```markdown
# <프로젝트명> 로드맵

## 최종 결과물

- 대상 사용자:
- 핵심 사용자 가치:
- 목표 제공 수준:
- 완성 상태:

## 서비스 완료 기준

1. <관찰 가능한 전체 서비스 완료 조건>

## 포함 범위

## 마일스톤

### M1. <이 단계에서 완성되는 결과>

- 의존 관계:
- 전환 기준:
- Feature 문서 후보: <kebab-case 이름>

## 최종 관문

<목표 제공 수준에 별도 관문이 필요한 경우에만 작성하고, 필요하지 않으면 이 섹션을 생략>

## 보류·제외 범위
```

## 금지
- feature별 `spec.md`·`analysis.md`·`implement.md`를 만들지 않는다.
- 체크박스(`- [ ]` / `- [x]`)를 두지 않는다. 두 문서는 정적 문서다.
- 마일스톤 안에 구현 순서·Task 목록·체크리스트를 두지 않는다 (`implement.md` 소관).
- feature 수준의 완료 조건을 여기서 확정하지 않는다 (`spec.md` §5 소관).

## 완료 조건
- `README.md`와 `ROADMAP.md`가 생성 또는 갱신되었다.
- `ROADMAP.md`에 최종 결과물, 서비스 완료 기준, 마일스톤 하나 이상이 있다.
- 각 마일스톤에 완성되는 결과, 의존 관계(없으면 "없음"), 전환 기준, feature 문서 후보 이름이 있다.
- 최종 관문은 목표 제공 수준에 필요한 경우에만 있다.
- `features/<feature-dir>/`는 생성되지 않았다.

## 완료 보고
- 생성 또는 갱신한 파일
- 최종 결과물, 서비스 완료 기준, 마일스톤의 구분
- 최종 관문, 보류·제외 범위와 재검토 조건
- 다음 단계로 `/spec-init`이 필요한 마일스톤별 feature 후보

## 후속 단계 계약
- `ROADMAP.md`의 feature 후보 이름이 `/spec-init <feature-name>`의 인자가 된다. 실행 시점은 사용자가 정한다(CLAUDE.md §phase 제어).
