> 사용 시점: 프로젝트 문서가 아직 없는 최초 1회. 이후 문서 갱신은 이 command 밖에서 처리한다.

프로젝트 루트에 `README.md`·`ROADMAP.md`·`docs/product.md`·`docs/design.md`를 만든다.

프로젝트 이름 또는 한 줄 설명: $ARGUMENTS

## 역할
- 실행 주체는 main이며 subagent에 맡기지 않는다.
- 다음 세션이 이전 대화 없이 프로젝트 목표와 현재 기준을 복원할 수 있는 정적 기준 문서다.
- 최종 결과물과 마일스톤별 실행 범위를 나누고, 초기에 구현 가능한 범위로 최종 목표를 줄이지 않는다.

## 대상 프로젝트 루트
- 사용자가 루트를 명시하면 그 경로와 거기 적용되는 프로젝트 `CLAUDE.md`를 따른다.
- 그 밖에는 지정된 파일·하위 디렉토리나 활성 작업 디렉토리에서 출발해, 적용되는 프로젝트 `CLAUDE.md`·VCS 루트·주요 manifest·빌드 설정으로 그 경로를 소유하는 루트를 찾는다.
  전역 `~/.claude/CLAUDE.md`는 모든 대화에 로드되므로 신호에서 뺀다.
- 후보가 하나면 근거와 함께 확정한다.
  모노레포 루트와 하위 프로젝트처럼 후보가 둘 이상이라 산출물이 달라지거나 신호가 없으면 파일을 만들기 전에 확인한다.
- 확정한 루트는 이후 조사·산출 경로의 기준이며, 근거는 완료 보고에 남긴다.

## 전제 조건
- §산출 경로의 네 파일 중 하나라도 있으면 최초 실행이 아니므로 아무 파일도 쓰지 않고 무엇이 있는지 보고한다.
- 인자가 비어 있으면 저장소·manifest에서 확인한 프로젝트 이름을 쓰고, 확인되지 않으면 묻는다.
- 최종 결과물·핵심 사용자·목표 제공 수준·서비스 완료 기준·포함 범위·보류 범위의 해석 차이가 결과를 바꾸면 쓰기 전에 묻는다(CLAUDE.md §요청 해석).
- 작성 전에 주요 manifest, 빌드·테스트 설정, 코드 구조, 사용자 입력을 확인한다.

## 산출 경로
확정한 루트 기준 `README.md`, `ROADMAP.md`, `docs/product.md`, `docs/design.md` 넷을 모두 만들고, 그 밖의 문서는 만들지 않는다.

## 작성 규칙
- 기술 선택·명령어·현재 동작·설치 방법·지원 기능·성능 목표·운영 보장은 확인한 파일이나 실행 결과에 근거해서만 적는다.
- 작업 후보는 kebab-case 이름으로만 제시한다.
- 보류·제외 범위는 사용자가 언급했거나 최종 결과물과 직접 경계를 이루는 항목만 적는다.
- 이번 입력에서 확정되지 않은 항목은 빈 자리로 남기지 않고 뺀다.
- 체크박스, 마일스톤 안의 구현 순서·작업 목록, 개별 작업의 완료 조건·검증 기준은 두지 않는다.
  ROADMAP이 다루는 완료 기준은 서비스 전체와 마일스톤 전환까지다.

## README.md 구조
세부 요구사항·마일스톤 계획·보류 판단 근거는 `ROADMAP.md`에 두고, 라이선스나 운영상 주의가 확인되면 마지막 섹션으로 더한다.

```markdown
# <프로젝트명>

## 개요
<프로젝트 이름과 한 줄 설명, 해결하려는 문제와 대상 사용자>

## 현재 상태

## 사용 방법
<확인된 설치·실행·사용 방법>

## 문서
- [ROADMAP.md](./ROADMAP.md)
- [docs/product.md](./docs/product.md)
- [docs/design.md](./docs/design.md)
```

## docs 문서 기준
두 문서는 README·ROADMAP의 책임에 담기 어려운 확정된 상세만 담는다.
- `docs/product.md` — 문서 목적과 다른 문서와의 관계, 대상 사용자·문제·핵심 사용자 흐름, 사용자에게 관찰되는 기능별 동작과 상태, 설정과 접근성, 사용자 관점의 데이터 보관·개인정보 정책, 현재 목표 범위와 이후 후보. 구현 계층·시스템 API·클래스 구조·작업 단위 계획은 넣지 않는다.
- `docs/design.md` — 문서 목적과 현재 구현·목표 설계의 구분, 기술 방향·아키텍처·책임 경계, 데이터·상태 흐름과 저장 정책, 내부·외부 인터페이스와 연동, 실패 처리와 복구 경계, 성능·정확성·안정성 검증 전략, 주요 기술 위험·대응·미확정 결정. 프로젝트 소개·릴리스 마일스톤·확인되지 않은 구현 세부는 넣지 않는다.

## 완료 보고
- 확인한 프로젝트 루트와 판단 근거
- 만든 파일과, 확정 정보가 없어 뺀 항목
- 최종 관문, 보류·제외 범위와 재검토 조건
