> 사용 시점: 프로젝트 최초 문서화 단계. Phased 흐름보다 앞서며, ROADMAP의 마일스톤별 feature 후보가 `/spec-init`의 입력이 된다.

프로젝트 루트 `README.md`와 `ROADMAP.md`를 작성하고, 조건에 따라 `docs/product.md`·`docs/design.md`를 함께 생성·갱신한다.
README는 프로젝트의 정체성·목적·현재 사용 방법·문서 진입점을 소유하고, ROADMAP은 최종 결과물·서비스 완료 기준·포함 범위·마일스톤·최종
관문·보류 범위를 소유하며, 선택 문서의 생성·갱신 조건과 담을 항목은 §선택 문서 기준이 소유한다.

프로젝트 이름 또는 한 줄 설명: $ARGUMENTS

## 역할
- 다음 세션에서 이전 대화 없이 읽어도 프로젝트 목표와 현재 기준을 복원할 수 있는 기준 문서다.
- 정적 문서이며 진행 상황을 추적하는 문서가 아니다. Task 단위 진행 상태는 feature `README.md`와 `implement.md`가 소유한다.
- 최종 결과물과 마일스톤별 실행 범위를 분리한다. 초기에 구현 가능한 범위를 최종 목표로 축소해 쓰지 않는다.

## 대상 프로젝트 루트
`/project-init`이 문서를 쓸 대상 디렉토리를 입력 형태별 근거로 정한다. 같은 판단이 필요한 다른 command는
이 섹션을 참조로 가리키고 절차를 다시 적지 않는다.

입력은 세 형태로 갈리고, 형태마다 근거 신호가 다르다.

- 사용자가 프로젝트 루트를 명시한 경우 → 그 경로와 거기 적용되는 프로젝트 `CLAUDE.md`를 우선한다.
- 사용자가 파일이나 하위 디렉토리만 지정한 경우 → 그 경로를 조사 출발점으로 두고, 적용되는 프로젝트
  `CLAUDE.md`·VCS 루트·주요 manifest를 대조해 그 경로를 소유하는 루트를 찾는다.
- 경로가 없는 경우 → 활성 작업 디렉토리, 적용되는 프로젝트 `CLAUDE.md`, VCS 루트, 주요 manifest와 빌드
  설정을 대조해 문서가 책임질 루트를 찾는다.

근거 신호는 프로젝트 `CLAUDE.md`, VCS 루트, 주요 manifest, 빌드 설정, 활성 작업 디렉토리다. 전역
`~/.claude/CLAUDE.md`는 모든 대화에 로드되어 신호로서 판정력이 없으므로 제외한다.

루트는 미확인·확인됨 두 상태만 갖는다. 후보가 하나면 근거와 함께 확인됨으로 넘어간다. 모노레포 루트와
하위 프로젝트처럼 후보가 둘 이상이고 선택에 따라 산출물이 달라지면, 문서를 만들기 전에 사용자에게
확인한다. 확인된 루트는 이후 조사·산출 경로가 해석하는 기준이 되고, 확인 근거는 완료 보고까지 남긴다.

루트를 확인하지 못한 채 현재 작업 디렉토리에 문서를 만들지 않는다.

## 전제 조건
- 이 command를 쓰는 경우는 새 프로젝트의 최초 문서 생성, 또는 루트 `README.md`·`ROADMAP.md` 초기 작성이다.
- 기능 추가, 공개 contract 변경, 여러 Task로 나눠야 하는 구현 작업은 `/spec-init`부터 시작한다.
- 이미 `ROADMAP.md`가 있고 특정 feature만 구체화하려는 요청이면 문서를 쓰지 않고 `/spec-init`이 필요하다고 보고한다.
- README 문구만 고치는 작고 명확한 변경은 이 command 없이 Per-Request로 처리한다.
- 인자가 비어 있으면 프로젝트 이름은 저장소·manifest에서 확인한 값을 쓰고, 확인되지 않으면 질문한다.
- 최종 결과물, 핵심 사용자, 목표 제공 수준, 서비스 완료 기준, 포함 범위, 보류 범위의 해석 차이가 결과를 바꾸면 문서 작성 전에 질문으로 정리한다(방식은
  CLAUDE.md §요청 해석).
- 미확정 판단이 남아 있으면 추정으로 채워 문서를 생성하지 않는다.

## 입력 조사와 정보 보존
- 작성 전에 다음을 조사 대상으로 확인한다 — 기존 `README.md`·`ROADMAP.md`·`docs/`, 주요 manifest,
  빌드·테스트 설정, 코드 구조, 사용자 입력.
- 조사에서 추린 의미 있는 정보는 유지·이동·보류·제거 네 갈래로 분류하고, 갈래마다 목적지가 다르다.
  - 유지 — 현재 문서의 같은 책임 자리에 남는다.
  - 이동 — 다른 책임 문서(ROADMAP이나 선택 문서)로 옮긴다. 옮긴 뒤 원래 의미와 제약이 유지되는지
    대조해야 이동이 끝난다.
  - 보류 — 아직 확정되지 않았으므로 ROADMAP의 보류·제외 범위나 후속 feature 문서의 판단으로 넘긴다.
  - 제거 — 중복, 폐기된 결정, 사용자가 명시적으로 제외한 정보만 해당하며, 대상과 이유를 완료 보고에
    남긴다.
- 기존 문서를 축약하거나 재구성할 때도 같은 분류를 거친다. 계속 유효한 정보가 분류 없이 사라지는 경로는
  두지 않는다.
- 근거 없이 지우지 않는다. 정보를 지울 때는 위 네 갈래 중 제거에 해당하는 근거를 든다.

## 산출 경로
- 프로젝트 루트 `README.md`
- 프로젝트 루트 `ROADMAP.md`
- `docs/product.md` — 생성·갱신 조건은 §선택 문서 기준을 따른다.
- `docs/design.md` — 생성·갱신 조건은 §선택 문서 기준을 따른다.
- `features/<feature-dir>/`와 그 아래 feature 문서는 만들지 않는다. 경로 규칙은 `commands/spec-init.md` §산출 경로가 소유한다.

## 덮어쓰기 규칙
- 두 문서 중 일부가 이미 있으면 §입력 조사와 정보 보존의 분류를 거쳐 필요한 섹션만 쓴다.
- 기존 `README.md`·`ROADMAP.md`나 feature 문서의 기준을 바꾸는 갱신은 영향 범위를 먼저 보고하고 사용자 확인을 받은 뒤 진행한다.

## 작성 규칙
- 기술 선택, 명령어, 현재 동작은 확인한 파일이나 실행 결과에 근거해서만 단정한다.
- 확인되지 않은 설치 방법, 실행 명령, 지원 기능, 성능 목표, 운영 보장은 추정으로 쓰지 않는다.
- 최종 관문에 근거 없는 운영 환경 요구사항을 관례적으로 추가하지 않는다.
- feature 문서 후보는 kebab-case 이름으로만 제시한다.
- 보류·제외 범위는 사용자가 언급했거나 최종 결과물과 직접 경계를 이루는 항목만 적는다.

## README.md 구조
프로젝트 성격에 맞게 간결하게 다음을 둔다.

- 프로젝트 이름과 한 줄 설명
- 해결하려는 문제와 대상 사용자
- 현재 상태
- 확인된 설치·실행·사용 방법
- 주요 문서 링크
- 라이선스나 운영상 주의가 확인된 경우 그 정보

세부 요구사항, 마일스톤 계획, 보류 항목의 판단 근거는 `ROADMAP.md`에 둔다. 문서 링크는 실제로 존재하는 문서만 연결하고, 선택 문서가 없으면
링크도 두지 않는다.

```markdown
# <프로젝트명>

## 개요

## 현재 상태

## 사용 방법

## 문서
- [ROADMAP.md](./ROADMAP.md)
- [docs/product.md](./docs/product.md) (있으면)
- [docs/design.md](./docs/design.md) (있으면)
```

## ROADMAP.md 구조
- 최종 결과물: 사용자가 기대하는 완성 상태, 핵심 사용자 가치와 목표 제공 수준
- 서비스 완료 기준: 대상 사용자가 최종 결과를 얻을 수 있음을 확인하는 관찰 가능한 조건
- 포함 범위: 최종 결과물에 포함되는 주요 기능
- 마일스톤: 이 단계에서 완성되는 검증 가능한 결과, 의존 관계(없으면 "없음"), 전환 기준, feature 문서 후보 이름만 둔다
- 최종 관문: 필요한 경우 여러 마일스톤에 공통으로 적용되는 품질·배포·운영 조건
- 보류·제외 범위: 제외 이유, 관련 위험과 다시 검토할 조건

```markdown
# <프로젝트명> 로드맵

## 최종 결과물

- 대상 사용자:
- 핵심 사용자 가치:
- 목표 제공 수준:
- 완성 상태:

## 서비스 완료 기준

1. <관찰 가능한 전체 서비스 완료 조건>

## 포함 범위

## 마일스톤

### M1. <이 단계에서 완성되는 결과>

- 의존 관계:
- 전환 기준:
- Feature 문서 후보: <kebab-case 이름>

## 최종 관문

<목표 제공 수준에 별도 관문이 필요한 경우에만 작성하고, 필요하지 않으면 이 섹션을 생략>

## 보류·제외 범위
```

## 선택 문서 기준
다음 네 조건 중 하나라도 해당하면 해당 문서를 생성하거나 갱신한다. 어느 것에도 해당하지 않으면 손대지 않는다. 두 문서에 같은 조건을
적용하며, 기존 선택 문서를 이번 입력에 상세가 없다는 이유만으로 지우거나 재작성하지 않는다.

- README·ROADMAP에 요약만 두면 의미 있는 사용자 동작이나 정책이 유실된다.
- 상세 내용을 README·ROADMAP에 두면 두 문서의 책임을 침범하거나 중복이 생긴다.
- 기존 선택 문서가 해당 정보의 기준 문서다.
- 사용자가 해당 문서를 명시적으로 요청했다.

아래 두 문서의 담을 항목은 프로젝트에 적용되는 것만 고른다.

### docs/product.md
담을 항목:
- 문서 목적과 다른 프로젝트 문서와의 관계
- 대상 사용자, 문제와 핵심 사용자 흐름
- 사용자에게 관찰되는 기능별 동작과 상태
- 설정과 접근성
- 데이터 보관과 개인정보에 대한 사용자 관점의 정책
- 현재 목표 범위와 이후 후보

넣지 않을 항목: 구현 계층, 시스템 API, 클래스 구조, Task 단위 계획

### docs/design.md
담을 항목:
- 문서 목적과 현재 구현·목표 설계의 구분
- 기술 방향, 아키텍처와 책임 경계
- 데이터와 상태 흐름, 저장 정책
- 내부·외부 인터페이스와 연동
- 실패 처리와 복구 경계
- 성능, 정확성, 안정성 검증 전략
- 주요 기술 위험, 대응과 미확정 결정

넣지 않을 항목: 프로젝트 소개, 릴리스 마일스톤, 확인되지 않은 구현 세부사항

## 금지
- 체크박스(`- [ ]` / `- [x]`)를 두지 않는다.
- 마일스톤 안에 구현 순서·Task 목록·체크리스트를 두지 않는다 (`implement.md` 소관).
- feature 수준의 완료 조건과 검증 기준을 여기서 확정하지 않는다 (`spec.md` §5 소관).
- `docs/product.md`·`docs/design.md` 밖의 다른 선택 문서와 `docs/` 아래 기능별 문서를 만들지 않는다.

## 완료 보고
- 확인한 프로젝트 루트와 그 판단 근거
- 유지·이동·보류·제거로 분류한 정보와 제거한 정보의 이유
- 생성 또는 갱신한 파일(선택 문서 포함)
- 최종 결과물·서비스 완료 기준·마일스톤을 서로 섞지 않고 각자 자리에 뒀는지
- 최종 관문, 보류·제외 범위와 재검토 조건
- 다음 단계로 `/spec-init`이 필요한 마일스톤별 feature 후보

## 후속 단계 계약
- `ROADMAP.md`의 feature 후보 이름이 `/spec-init <feature-name>`의 인자가 된다. 실행 시점은 사용자가 정한다(CLAUDE.md §phase 제어).
