> 사용 시점: 프로젝트 문서가 아직 없는 최초 1회. 이후 문서 갱신은 이 command 밖에서 처리한다.

프로젝트 루트에 `README.md`·`ROADMAP.md`·`docs/product.md`·`docs/design.md`를 만든다.
네 문서가 각각 무엇을 소유하는지는 §README.md 구조·§ROADMAP.md 구조·§docs 문서 기준이 정한다.

프로젝트 이름 또는 한 줄 설명: $ARGUMENTS

## 역할
- 다음 세션에서 이전 대화 없이 읽어도 프로젝트 목표와 현재 기준을 복원할 수 있는 기준 문서다.
- 정적 문서이며 진행 상황을 추적하는 문서가 아니다.
- 최종 결과물과 마일스톤별 실행 범위를 분리한다. 초기에 구현 가능한 범위를 최종 목표로 축소해 쓰지 않는다.

## 대상 프로젝트 루트
문서를 쓸 대상 디렉토리를 근거로 정한다. 같은 판단이 필요한 다른 command는 이 섹션을 참조로 가리키고 절차를 다시 적지 않는다.

- 사용자가 프로젝트 루트를 명시한 경우 → 그 경로와 거기 적용되는 프로젝트 `CLAUDE.md`를 우선한다.
- 그 밖에는 사용자가 지정한 파일·하위 디렉토리나 활성 작업 디렉토리를 출발점으로 두고, 적용되는 프로젝트 `CLAUDE.md`·VCS 루트·주요
  manifest·빌드 설정을 대조해 그 경로를 소유하는 루트를 찾는다. 전역 `~/.claude/CLAUDE.md`는 모든 대화에 로드되어 판정력이 없으므로
  신호에서 뺀다.

루트는 미확인·확인됨 두 상태만 갖는다. 후보가 하나면 근거와 함께 확인됨으로 넘어간다. 모노레포 루트와 하위 프로젝트처럼 후보가 둘 이상이라
선택에 따라 산출물이 달라지거나, 신호가 하나도 없으면 파일을 만들기 전에 사용자에게 확인한다. 확인된 루트는 이후 조사·산출 경로를 해석하는
기준이 되고, 확인 근거는 완료 보고까지 남긴다. 미확인 상태로 현재 작업 디렉토리에 파일을 만들지 않는다.

## 전제 조건
- §산출 경로의 네 파일 중 하나라도 이미 있으면 최초 실행이 아니므로 아무 파일도 쓰지 않고 무엇이 있는지 보고한다.
- 인자가 비어 있으면 프로젝트 이름은 저장소·manifest에서 확인한 값을 쓰고, 확인되지 않으면 질문한다.
- 최종 결과물, 핵심 사용자, 목표 제공 수준, 서비스 완료 기준, 포함 범위, 보류 범위의 해석 차이가 결과를 바꾸면 문서 작성 전에 질문으로
  정리한다(방식은 CLAUDE.md §요청 해석).

## 조사 대상
작성 전에 주요 manifest, 빌드·테스트 설정, 코드 구조, 사용자 입력을 확인한다.

## 산출 경로
확인된 프로젝트 루트 기준 네 파일이며 모두 만든다.

- `README.md`
- `ROADMAP.md`
- `docs/product.md`
- `docs/design.md`

## 작성 규칙
- 기술 선택, 명령어, 현재 동작, 설치 방법, 지원 기능, 성능 목표, 운영 보장은 확인한 파일이나 실행 결과에 근거해서만 적는다.
- 최종 관문에 근거 없는 운영 환경 요구사항을 관례적으로 추가하지 않는다.
- 작업 후보는 kebab-case 이름으로만 제시한다.
- 보류·제외 범위는 사용자가 언급했거나 최종 결과물과 직접 경계를 이루는 항목만 적는다.

## README.md 구조
프로젝트 성격에 맞게 간결하게 다음을 둔다. 세부 요구사항, 마일스톤 계획, 보류 항목의 판단 근거는 `ROADMAP.md`에 둔다.

- 개요: 프로젝트 이름과 한 줄 설명, 해결하려는 문제와 대상 사용자
- 현재 상태
- 사용 방법: 확인된 설치·실행·사용 방법
- 문서: 나머지 세 문서 링크
- 라이선스나 운영상 주의가 확인된 경우 그 정보를 마지막 섹션으로 더한다

```markdown
# <프로젝트명>

## 개요

## 현재 상태

## 사용 방법

## 문서
- [ROADMAP.md](./ROADMAP.md)
- [docs/product.md](./docs/product.md)
- [docs/design.md](./docs/design.md)
```

## ROADMAP.md 구조
- 최종 결과물: 사용자가 기대하는 완성 상태, 핵심 사용자 가치와 목표 제공 수준
- 서비스 완료 기준: 대상 사용자가 최종 결과를 얻을 수 있음을 확인하는 관찰 가능한 조건
- 포함 범위: 최종 결과물에 포함되는 주요 기능
- 마일스톤: 이 단계에서 완성되는 검증 가능한 결과, 의존 관계(없으면 "없음"), 전환 기준, 작업 후보 이름만 둔다
- 최종 관문: 여러 마일스톤에 공통으로 적용되는 품질·배포·운영 조건이 확인된 경우에만 둔다
- 보류·제외 범위: 제외 이유, 관련 위험과 다시 검토할 조건

```markdown
# <프로젝트명> 로드맵

## 최종 결과물

- 대상 사용자:
- 핵심 사용자 가치:
- 목표 제공 수준:
- 완성 상태:

## 서비스 완료 기준

1. <관찰 가능한 전체 서비스 완료 조건>

## 포함 범위

## 마일스톤

### M1. <이 단계에서 완성되는 결과>

- 의존 관계:
- 전환 기준:
- 작업 후보: <kebab-case 이름>

## 최종 관문

<여러 마일스톤에 공통으로 적용되는 관문이 확인된 경우에만 작성하고, 없으면 이 섹션을 생략>

## 보류·제외 범위
```

## docs 문서 기준
두 문서는 README·ROADMAP의 책임에 담기 어려운 확정된 상세를 소유한다. 아래 담을 항목은 프로젝트에 적용되고 이번 입력에서 확정된 것만
고르며, 확정되지 않은 항목은 빈 자리로 남기지 않는다.

### docs/product.md
담을 항목:
- 문서 목적과 다른 프로젝트 문서와의 관계
- 대상 사용자, 문제와 핵심 사용자 흐름
- 사용자에게 관찰되는 기능별 동작과 상태
- 설정과 접근성
- 데이터 보관과 개인정보에 대한 사용자 관점의 정책
- 현재 목표 범위와 이후 후보

넣지 않을 항목: 구현 계층, 시스템 API, 클래스 구조, 작업 단위 계획

### docs/design.md
담을 항목:
- 문서 목적과 현재 구현·목표 설계의 구분
- 기술 방향, 아키텍처와 책임 경계
- 데이터와 상태 흐름, 저장 정책
- 내부·외부 인터페이스와 연동
- 실패 처리와 복구 경계
- 성능, 정확성, 안정성 검증 전략
- 주요 기술 위험, 대응과 미확정 결정

넣지 않을 항목: 프로젝트 소개, 릴리스 마일스톤, 확인되지 않은 구현 세부사항

## 금지
- 체크박스(`- [ ]` / `- [x]`)를 두지 않는다.
- 마일스톤 안에 구현 순서·작업 목록·체크리스트를 두지 않는다.
- 개별 작업의 완료 조건과 검증 기준은 확정하지 않는다. ROADMAP이 다루는 완료 기준은 서비스 전체와 마일스톤 전환까지다.
- §산출 경로의 네 파일 밖에 다른 문서를 만들지 않는다.

## 완료 보고
- 확인한 프로젝트 루트와 그 판단 근거
- 만든 파일과, 각 문서에서 확정 정보가 없어 비워 둔 항목
- 최종 관문, 보류·제외 범위와 재검토 조건

## 핵심 질문
> 이 프로젝트는 최종적으로 무엇을 제공하며, 어떤 관찰 가능한 조건에서 서비스가 완료되었다고 보고, 거기까지 어떤 마일스톤을 거치는가?
