프로젝트 루트에 `README.md`·`ROADMAP.md`·`docs/product.md`·`docs/design.md`를 만든다.

프로젝트 이름 또는 한 줄 설명: $ARGUMENTS

## 역할
- main이 직접 쓴다.
- 다음 세션이 대화 없이도 프로젝트 목표와 현재 기준을 알 수 있게 하는 문서다.
- 최종 결과물과 마일스톤별 범위를 나눠 적는다.

## 대상 프로젝트 루트
- 사용자가 루트를 알려 주면 그 경로와 거기 적용되는 프로젝트 `CLAUDE.md`를 따른다.
- 아니면 지정된 파일이나 작업 디렉토리에서 출발해, 프로젝트 `CLAUDE.md`·VCS 루트·manifest·빌드 설정으로 루트를 찾는다.
- 전역 `~/.claude/CLAUDE.md`는 어디서나 로드되므로 단서로 쓰지 않는다.
- 후보가 하나면 근거와 함께 정한다.
- 모노레포처럼 후보가 여럿이라 결과가 달라지거나, 단서가 없으면 파일을 만들기 전에 묻는다.

## 전제 조건
- §산출 경로의 네 파일 중 하나라도 있으면 아무것도 쓰지 않고 무엇이 있는지 알린다.
- 인자가 없으면 저장소·manifest에서 프로젝트 이름을 찾고, 없으면 묻는다.

## 산출 경로
루트의 `README.md`, `ROADMAP.md`, `docs/product.md`, `docs/design.md` 넷을 모두 만든다.
다른 문서는 만들지 않는다.

## 작성 규칙
- 기술, 명령어, 현재 동작, 성능, 운영 같은 사실은 확인한 파일이나 실행 결과로만 적는다.
- 작업 후보는 kebab-case 이름만 적는다.
- 보류·제외 범위는 사용자가 말했거나 최종 결과물의 경계가 되는 것만 적는다.
- 정해지지 않은 항목은 빈칸으로 두지 말고 뺀다.
- 체크박스, 마일스톤 안의 작업 순서·목록, 개별 작업의 완료 조건은 넣지 않는다.
- ROADMAP의 완료 기준은 서비스 전체와 마일스톤 전환까지만 다룬다.

## README.md 구조
- 세부 요구사항, 마일스톤 계획, 보류 이유는 ROADMAP.md에 둔다.
- 라이선스나 운영 주의사항이 확인되면 마지막 섹션으로 넣는다.

```markdown
# <프로젝트명>

## 개요
<프로젝트 이름과 한 줄 설명, 해결하려는 문제와 대상 사용자>

## 현재 상태

## 사용 방법
<확인된 설치·실행·사용 방법>

## 문서
- [ROADMAP.md](./ROADMAP.md)
- [docs/product.md](./docs/product.md)
- [docs/design.md](./docs/design.md)
```

```markdown
## 최종 결과물

- 대상 사용자:
- 핵심 사용자 가치:
- 목표 제공 수준:
- 완성 상태:

## 서비스 완료 기준

1. <밖에서 확인할 수 있는 서비스 전체 완료 조건>

## 포함 범위
<최종 결과물에 들어가는 주요 기능>

## 마일스톤

### M1. <이 단계에서 완성되는 결과>

- 의존 관계: <없으면 "없음">
- 전환 기준:
- 작업 후보: `<kebab-case 이름>`

## 최종 관문

<여러 마일스톤에 공통으로 걸리는 관문이 확인됐을 때만 쓰고, 없으면 이 섹션을 뺀다>

## 보류·제외 범위
<제외한 이유, 관련 위험, 다시 검토할 조건>
```

## docs 문서
README와 ROADMAP에 넣기 어려운, 확정된 상세 내용만 담는다.
- `docs/product.md` — 사용자 관점: 대상 사용자와 문제, 핵심 흐름, 기능별 동작, 사용자에게 적용되는 정책, 현재 목표 범위. 구현 구조와 작업 계획은 넣지 않는다.
- `docs/design.md` — 기술 관점: 현재 구현과 목표 설계의 구분, 아키텍처와 책임 경계, 데이터·상태 흐름, 인터페이스, 실패 처리, 검증 방법, 기술 위험과 미정 사항. 프로젝트 소개, 마일스톤, 확인 안 된 구현 세부는 넣지 않는다.

## 완료 보고
- 프로젝트 루트와 그렇게 판단한 근거
- 만든 파일, 정보가 없어 뺀 항목
- 최종 관문, 보류·제외 범위와 다시 검토할 조건
