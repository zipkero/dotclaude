> 사용 시점: 전역설정에 변경이 누적되었을 때, 또는 런타임 모델 세대가 바뀌었을 때 사용자가 의식적으로 호출한다.
> 전역 감사에서는 Anthropic 공식 자료의 최신 권고를 확인해 판정 기준으로 삼고, 참조한 권고는 보고에 출처와 함께 남긴다.
> 확인 대상은 Claude Code 공식 문서, prompting best practices, Anthropic 엔지니어링 블로그와 릴리스 노트다.
> 모델 세대가 바뀐 뒤라면 그 세대의 모델 문서와 릴리스 노트를 함께 본다.
> 권고를 판정 근거로 쓸 때는 그 권고가 겨냥한 상황과 판정 대상이 같은 종류인지 먼저 확인한다.
> 대상 설정이 그 권고의 전제와 다른 목적을 가지면(예: 품질 향상용 절차가 아니라 상태 전환을 남기는 게이트),
> 권고를 그대로 적용하지 않고 어긋나는 지점을 근거와 함께 밝힌다.
> 이 환경에서 관찰한 동작과 공식 문서가 보장하는 범위는 구분해 적고, 관찰값을 공식 보장처럼 일반화하지 않는다.

전역설정을 다시 읽고 §점검 항목의 관점을 적용해 분석한다.

## 실행 주체와 범위
- 실행 주체: main이 직접 수행한다. 전 파일 정독과 감사 판단이 한 몸이므로 로컬 파일 탐색을 subagent에 위임하지 않는다.
- 외부 자료 확인: main이 WebSearch·WebFetch로 머리말이 정한 확인 대상을 직접 가져와 대조하며, 기억으로 대신하지 않는다.
  가져오지 못한 자료는 그 사실을 보고에 적고 판정 근거로 쓰지 않는다.
- 분석 범위: 전역설정 디렉토리(`~/.claude`)에서 `git ls-files`로 조회되는 추적 파일 전체. 파일마다 §점검 항목 중 해당하는 관점을
  적용하고, 어느 관점에도 걸리지 않는 추적 파일은 다른 추적 파일의 진술과 어긋나는지만 본다.
- 컨텍스트 로딩: 사용자가 특정 파일이나 skill을 대상으로 지정하면 그 대상과 판단에 직접 필요한 참조만 읽는다.
  분석 범위 전체를 읽는 것은 전역 감사 요청일 때만이다.

## 점검 항목

### 역할 프롬프트 충분성 (`agents/**`, `commands/**`, `skills/**`)
1. 각 파일이 자기 역할의 책임, 필수 입력, 판단 기준, 출력, 중단 조건, 제외 범위를 정의하는가.
2. 실행 절차만 있고 판단 기준·실패 처리·근거 부족 시 처리가 없으면 불충분으로 본다.
3. 역할 설명이 짧거나 추상적이어서 핵심 판단이 모델 재량에 통째로 맡겨져 있으면 `부족`으로 판정한다.
   단, 판정은 §context health의 기준 모델 규칙을 따르며, 일반 지시만으로 안정적인 판단까지 기준 부재로 보지 않는다.
4. frontmatter `description`이 실제 발동 조건과 역할 범위를 드러내는가.

### 책임 경계
1. 각 역할이 소유하는 결정과 소유하지 않는 결정이 구분되는가.
2. main·agent·skill 사이의 파일 수정 권한, 상태 전환 권한, 최종 판단 권한이 섞여 있지 않은가.
3. frontmatter `description`이 정의한 역할과 본문에 호스팅된 정책이 어긋나지 않는가
   (예: skill A의 본문이 skill B·command C가 소유해야 할 작성 정책을 호스팅하는 경우).
4. 다른 파일이 소유한 기준을 재정의하거나 암묵적으로 대체하는 문구가 없는가.
5. 한 결정을 여러 파일이 조각으로 나눠 들고 있어, 판단하려면 파일을 여러 번 오가야 하지 않는가.
   소비 주체나 로딩 시점이 달라서 갈라야 할 이유가 없는데 쪼개져 있으면 §context health 1의 통합 대가 판정을 적용해 통합 후보로 낸다.

### 플로우 완결성
1. 각 phase 산출물이 이전 대화 맥락 없이 그 문서(와 선행 산출물)만으로 다음 phase를 진행할 수 있게 하는 기준을 갖는가.
2. phase가 중간에 끊겨도 다음 phase가 기존 문서와 사용자 지시만으로 재개될 수 있는가.
3. 승인 전 확인, 미해결 Decision Point, 접근 이탈 보고, 검증할 변경 범위가 다음 단계에서 무시되거나 대화 기억에만 의존하지 않는가.
4. `CLAUDE.md` §agent·skill 라우팅이 정한 위임과 각 command·skill·agent 본문의 위임 진술이 같은 흐름을 가리키는가.
   판정할 때는 진입 지점부터 실행 주체까지 체인을 따라가 주체가 바뀌는 자리를 확인한다.
5. 소유권을 넘기는 참조가 실제로 닿는가 — 가리킨 파일과 섹션이 존재하고, 그 자리가 정말 그 기준을 들고 있는가.
6. 어느 흐름에서도 호출되지 않고 사용자 진입 지점도 아닌 command·skill·agent가 남아 있지 않은가.

### 룰 파일 (`CLAUDE.md`, `agents/**`, `commands/**`, `skills/**`, `rules/**`)
1. 룰 간 의미 충돌·모순
2. 모호하거나 불필요하게 어려운 표현 (정의되지 않은 비유어, 소유 위치 불명, 쉬운 말로 같은 뜻이 되는 조어·한자어)
3. 영어식 표현·직역체: `CLAUDE.md` §언어가 정한 예외 밖의 영어·직역체를 자연스러운 한국어로 쓰는가.
4. `CLAUDE.md` 자기 룰 위반 (응답 룰, 용어 선택 룰을 스스로 어기는 경우)
5. 줄일 곳: 의미가 달라지지 않는 선에서 줄일 수 있는 부분 — 같은 소유 위치 안의 비슷한 표현 반복, 동일 개념의 재진술, 규칙 하나를 필요 이상으로 길게
   푼 장황한 문장. 삭제 후보의 판정 질문은 "이 줄을 지우면 실수가 생기는가"이고,
   재작성 후보의 판정 질문은 "짧게 쓴 판이 원본과 같은 것을 지시하는가"다.
   압축안은 제안 표현 자체에 항목 2를 적용해, 짧아지면서 판단 지점이 흐려지는 안은 후보에서 뺀다.
6. Bullet 단위 단일성: 한 bullet에 의미 단위가 다른 독립 주장이 둘 이상 묶여 있지 않은가? 묶여 있으면 의미 단위로 줄을 나눠 'bullet 하나당 하나의 룰'
   구조를 유지한다.
7. 추상 수준 적정성: 구체 예시·트리 형태 나열·도구 사용 패턴이 룰의 본질을 가리거나 적용 범위를 좁히지 않는가? 추상 원칙으로 의미가 전달되면 예시
   부분은 줄인다.
8. 긍정형 표현 우선: 룰은 "...한다"의 긍정 단언을 기본으로 한다. 부정형(`...하지 않는다`, `...아니다`)이 앞·뒤 긍정형과 같은 의미라서 뜻을 더하지 않고
   따라 붙은 경우에는 군더더기로 보고 정리한다. anti-pattern을 직접 막는 부정 단언과 `금지` 섹션처럼 부정 단언이 소유자인 자리는 그대로 둔다.
9. 게이트 발동 조건 적정성: 질문·중단·사전 확인을 요구하는 룰이 "결과에 실질적 영향" 같은 한정 기준 없이
   광범위하게 발동하도록 쓰여 있지 않은가? 넓은 게이트는 진행을 막고, 발동 여부 판단 자체가 추론을 소모한다.
   단, 되돌리기 어렵거나 외부에 영향을 주는 조치의 게이트는 넓어도 정당하며 이 항목으로 좁히지 않는다.
10. 로딩 시점 정합성: 룰이 적용돼야 하는 순간에 실제로 컨텍스트에 들어오는가. 파일 종류로 걸리는 기준은 `rules/**`의 `paths`가,
    특정 흐름에서만 필요한 기준은 그 흐름의 command·skill이, 어느 대화에서든 필요한 기준은 `CLAUDE.md`가 들고 있어야 한다.
    `CLAUDE.md`는 모든 대화에 항상 로드되므로 특정 상황에서만 의미 있는 운영 상세가 끼어 있으면, 또는 본문이 발동하지 않는 파일에 있고
    적용 지점에는 참조 한 줄만 남아 있으면 오배치로 본다.

### Context health
다음 신호가 보이면 context pollution 또는 설정 과잉으로 보고 원인 파일과 축소 후보를 제시한다.
모델 역량을 근거로 판정할 때 기준 모델은 소비 주체를 따른다 — agent frontmatter에 `model`이 고정되어 있으면 그 모델, 아니면 main 모델이며,
한 파일을 여러 주체가 소비하면(예: `skills/implement/SKILL.md`) 가장 약한 소비 모델 기준으로 판정한다.

1. 같은 규칙이 `CLAUDE.md`, command, skill, agent에 반복 정의되어 있다. 판정 전에 그 파일들이 같은 컨텍스트에 함께 로드되는지 본다 —
   호출 주체가 달라 함께 로드되지 않으면 컨텍스트 비용은 없고 드리프트 위험만 남으므로, 통합 대가와 견줘 판정한다.
2. command·skill 파일이 자기 발동 범위 밖의 정책까지 설명한다.
3. agent 본문이 위임 역할보다 절차를 많이 들고 있다.
4. `README.md`가 실제 동작 설명을 넘어 운영 규칙의 소유자처럼 동작한다.
5. 오래된 인수인계·임시 메모·실험 기록이 공식 룰처럼 남아 있다.
6. 개별 항목에 문제가 없어도 설정 총량 자체가 커져 로드 비용이 늘고 있다. 전역 감사에서는 파일별 분량을 훑고 §룰 파일 5의 기준으로 압축 후보를
   함께 제시한다.
   단, 파일·흐름을 통째로 덜어내자는 제안은 그 경로의 실사용 빈도를 사용자에게 확인한 뒤에만 한다.
   분량과 구조만으로는 그 설정이 값을 하는지 판정할 수 없다.
7. 역량 보상형 지시의 군더더기화: 모델의 약점을 메우려 박아 둔 지시(장황한 절차 나열, anti-pattern 반복 경고, 같은 강조의 재진술)가 그 지시를 소비하는
   주체의 모델 기준으로 불필요해졌는가.
   정적 판정은 추정이므로 결론은 "제거"가 아니라 "제거 후보 + 그 지시가 막던 실패 가설"로 낸다.
   정책·계약형 지시(언어·폴더 구조·소유권·출력 형식·부작용 제한)는 모델과 무관하게 유지 대상이며 이 항목으로 줄이지 않는다.
8. 하네스 중복: Claude Code 시스템 프롬프트가 이미 강제하는 동작(결론 우선 보고, 전용 도구 사용 등)을
   설정 파일이 재진술하고 있다. 재진술은 제거 후보로 제시하되, 하네스 기본값과 다른 방향을 지정하는 룰은 중복이 아니다.
   그런 룰은 반대로 기본값에 밀리지 않을 만큼 쓰여 있는지를 본다 — 발동 자리와 우선순위 없이 한 줄로만 적혀 있으면 보강 후보로 낸다.
   판정 범위는 그 파일을 읽는 주체로 한정한다 — subagent는 CLAUDE.md는 받지만 main의 시스템 프롬프트는 받지 않으므로,
   `CLAUDE.md` 룰은 agent 소비자가 하나라도 있으면 하네스 중복으로 보지 않는다.

### `README.md` (프로젝트 자체에 대한 설명)
규칙 어긋남 점검은 적용하지 않는다. 대신 다음을 본다.
- 설명이 실제 구조·기능과 일치하는가 (`CLAUDE.md`, `commands/**`, `skills/**`, `agents/**`의 실제 동작과 어긋난 진술이 있는지)
- 폐기되었거나 더 이상 존재하지 않는 기능·구조가 남아 있는가
- 새로 추가된 기능·파일이 `README.md`에 누락되어 있는가
- 표기·예시·링크가 깨졌는가

## 출력 형식
- 전체 판정: `정상`, `과함`, `부족`, `충돌` 중 하나. 역할 프롬프트가 불충분하면 충돌이 없어도 `부족`,
  context health가 나쁘면 충돌이 없어도 `과함`으로 판정한다.
- 역할 프롬프트 판정 (파일별): `충분` / `부분 부족` — 판단 기준·실패 처리·책임 경계 중 일부가 약하다 / `부족`.
  판정 기준은 §역할 프롬프트 충분성을 따른다.
- 각 발견에 대해 위치(파일·섹션) + 현재 표현 + 제안 표현(before/after diff)
- 발견은 두 부류로 나눠 표시한다.
  `문구` — 표현·중복·위치·일관성만 바뀌고 동작은 그대로인 것.
  `동작` — 적용하면 실제 행동이 달라지는 것. 이 부류는 diff와 별도로 "적용 후 무엇이 달라지는지"를
  참조 식별자 없는 평문 한두 줄로 함께 적는다.
- 파일이 아니라 사용자 발언을 근거로 삼은 발견은 그 사실을 표시하고, 발언의 해석을 먼저 확인한 뒤 제안을 만든다.
  확인 전에는 그 발언 위에 다른 발견을 쌓지 않는다.
- 위치 오배치 진단의 경우: 현재 위치 → 제안 위치 + 옮겨야 할 사유
- 우선순위 묶음: 역할 프롬프트 충분성·책임 경계·플로우 완결성 > 의미 충돌·게이트 적정성 > 공식 권고 어긋남 > 위치 오배치 >
  context health·하네스 중복 > 모호·영어식 표현 > 중복·축소 > 추상 수준·긍정형·bullet 단일성 > 자기 룰 위반
- `README.md` 부정확 항목은 별도 묶음으로 분리해 보고
- 다른 파일에도 함께 갱신해야 하는지 명시
- 발견 사항이 없으면 그렇게 말하되, 확인한 파일 범위와 남은 위험을 함께 적는다.

## 제외
- 요청 없는 자동 수정 — `동작` 부류의 적용은 사용자의 명시 승인 후에만 진행한다.
  `문구` 부류는 사용자가 적용을 요청하면 개별 확인 없이 한 번에 적용하고, 무엇을 고쳤는지 보고한다.
- 선호나 일반론만 근거로 한 문구 변경 제안.
- 새 워크플로우·정책 체계의 설계 확장 — 감사는 현재 설정의 판정까지만 한다.
  현재 역할의 통합·분리 후보는 판정에 들어가므로 이 항목으로 막지 않는다.

## 핵심 질문
> 각 룰이 소유자 파일에 있고, 각 역할 파일이 모델 재량에 기대지 않을 만큼 쓰여 있는가?
