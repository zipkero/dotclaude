> 사용 시점: 전역설정에 변경이 누적되었을 때, 또는 런타임 모델 세대가 바뀌었을 때 사용자가 의식적으로 호출한다.

전역설정을 다시 읽고 §점검 항목의 관점을 적용해 분석한다.

## 실행 주체와 범위
- 실행 주체: main이 직접 수행한다. 전 파일 정독과 감사 판단이 한 몸이므로 로컬 파일 탐색을 subagent에 위임하지 않는다.
- 외부 자료 확인: §공식 권고 대조의 확인 대상은 WebSearch·WebFetch로 직접 가져오며 기억으로 대신하지 않는다.
  가져오지 못한 자료는 그 사실을 보고에 적고 판정 근거로 쓰지 않는다.
- 분석 범위: 전역설정 디렉토리(`~/.claude`)에서 `git ls-files`로 조회되는 추적 파일 전체.
  어느 관점에도 걸리지 않는 추적 파일은 다른 추적 파일의 진술과 어긋나는지만 본다.
- 컨텍스트 로딩: 사용자가 특정 파일이나 skill을 대상으로 지정하면 그 대상과 판단에 직접 필요한 참조만 읽는다.
- 판정 기준: 이 설정을 읽고 실행하는 주체는 모델이다. 사람이 읽기 좋은가가 아니라 소비 모델이 안정적으로 따르는가로 판정한다.
- 기준 모델: 소비 주체를 따른다 — agent frontmatter에 `model`이 고정되어 있으면 그 모델, 아니면 main 모델이며,
  한 파일을 여러 주체가 소비하면(예: `skills/implement/SKILL.md`) 가장 약한 소비 모델 기준으로 판정한다.

## 점검 항목

### 역할 프롬프트 충분성 (`agents/**`, `commands/**`, `skills/**`)
1. 각 파일이 자기 역할의 책임, 필수 입력, 출력을 정의하는가.
2. 판단 기준·중단 조건은 모델 재량에 맡긴다.
   그 재량이 이 환경에서 실제로 잘못된 결과를 냈을 때만 `부족`으로 판정하며, 판정은 §실행 주체와 범위의 기준 모델 규칙을 따른다.
3. frontmatter `description`이 실제 발동 조건과 역할 범위를 드러내는가.
4. 절차가 만들라고 지시한 산출물이 그 파일의 출력 형식에 자리를 갖는가.
   출력 형식이 항목을 닫아 둔 경우(`이 항목 외에 추가하지 않는다`) 절차가 지시한 항목이 그 목록에 있는지 본다.

### 책임 경계
1. 각 역할이 소유하는 결정과 소유하지 않는 결정이 구분되는가.
2. main·agent·skill 사이의 파일 수정 권한, 상태 전환 권한, 최종 판단 권한이 섞여 있지 않은가.
3. frontmatter `description`이 정의한 역할 범위 밖의 정책을 본문이 호스팅하지 않는가.
4. 다른 파일이 소유한 기준을 소유자 쪽 표시 없이 대체하는 문구가 없는가.

### 플로우 완결성
1. 각 phase 산출물이 이전 대화 맥락 없이 그 문서(와 선행 산출물)만으로 다음 phase와 중단된 세션을 재개하게 하는가.
2. 승인 전 확인, 미해결 Decision Point, 접근 이탈 보고, 검증할 변경 범위, 재작성으로 무효가 된 승인 상태가
   다음 단계에서 무시되거나 대화 기억에만 의존하지 않는가.
3. `CLAUDE.md` §agent·skill 라우팅이 정한 위임과 각 파일의 위임 진술이 같은 흐름을 가리키는가.
   진입 지점부터 실행 주체까지 체인을 따라가 주체가 바뀌는 자리를 확인한다.
4. 소유권을 넘기는 참조가 실제로 닿는가 — 가리킨 파일과 섹션이 존재하고, 그 자리가 정말 그 기준을 들고 있는가.
   한 문서를 쓰는 파일과 읽는 파일이 나뉘어 있으면 쓰는 쪽의 출력 형식과 읽는 쪽이 전제하는 구조가 같은지도 본다.
   문서를 가로지르는 영구 식별자(`SPEC §5.N`, `task-<nnn>`)는 만드는 파일과 참조·폐기하는 파일이 같은 수명 규칙을 쓰는지 본다.
5. 뒤로 돌아가는 경로가 정의돼 있는가 — 산출물 재작성, 확정된 요구사항·결정의 철회, 승인 상태 되돌리기.
   그 경로를 선택지로 제시하는 파일과 실제로 실행하는 파일이 같은 규칙을 쓰는지 본다.
6. 어느 흐름에서도 호출되지 않고 사용자 진입 지점도 아닌 command·skill·agent가 남아 있지 않은가.

### 룰 파일 (`CLAUDE.md`, `agents/**`, `commands/**`, `skills/**`, `rules/**`)
1. 룰 간 의미 충돌·모순이 있는가.
2. 표현이 한 갈래로 읽히는가 — 정의되지 않은 비유어, 소유 위치 불명, 쉬운 말로 같은 뜻이 되는 조어·한자어,
   두 해석이 실제로 다른 결과를 내는 문장, `CLAUDE.md` §언어가 정한 예외 밖의 영어·직역체,
   한 bullet에 묶인 둘 이상의 독립 주장, 추상 원칙으로 전달되는데 적용 범위를 좁히는 구체 예시 나열.
3. 같은 것을 여러 자리가 나눠 들고 있는가 — 한 파일 안의 재진술, 여러 파일의 반복 정의,
   한 결정이 조각나 판단하려면 파일을 여러 번 오가야 하는 형태.
   판정 전에 그 자리들이 같은 컨텍스트에 함께 로드되는지 본다.
   함께 로드되지 않으면 컨텍스트 비용이 없으므로, 그 자리들이 이미 어긋나 있을 때만 §룰 파일 1의 충돌로 낸다.
   통합 후보의 판정 질문은 "합친 판이 원본과 같은 것을 지시하는가"다.
4. 방어 지침이 값을 하는가 — 룰이 오작동할까 봐 붙인 예외 단서, 그 예외가 오용될까 봐 다시 붙인 단서,
   같은 말을 강도만 올려 되풀이한 경고, 앞줄이 이미 지시한 것을 다시 못 박는 줄, 모델이 못 할까 봐 풀어 쓴 절차 나열.
   판정 질문은 "이 줄을 지우면 어떤 실수가 생기는가"이고, 막는 실패를 지목하지 못하면 제거로 낸다.
   기본값은 제거이고 유지하려는 쪽이 근거를 댄다.
   예외 단서가 여럿 붙어 있으면, 뒤에 붙일 것이 아니라 룰의 발동 조건 자체를 좁혀야 한다는 뜻이다.
5. 질문·중단·사전 확인을 요구하는 룰이 되돌릴 수 있는 국소 변경까지 한정 기준 없이 발동하도록 쓰여 있지 않은가.
   넓은 게이트는 진행을 막고, 발동 여부 판단 자체가 추론을 소모한다.
6. 룰이 적용돼야 하는 순간에 실제로 컨텍스트에 들어오는가.
   파일 종류로 걸리는 기준은 `rules/**`의 `paths`가, 특정 흐름에서만 필요한 기준은 그 흐름의 command·skill이,
   어느 대화에서든 필요한 기준은 `CLAUDE.md`가 들고 있어야 한다.
   본문이 발동하지 않는 파일에 있고 적용 지점에는 참조 한 줄만 남아 있으면 오배치로 본다.
7. `CLAUDE.md`가 자기 룰(응답 룰, 용어 선택 룰)을 스스로 어기지 않는가.

### 공식 권고 대조
확인 대상은 다음 출처에서 직접 가져온 문서로 한정한다. 요약·재게시·비공식 정리글은 근거로 쓰지 않는다.

- `code.claude.com/docs` — Claude Code 문서.
- `platform.claude.com/docs` — 모델 문서, 릴리스 노트, prompt engineering.
  prompt engineering 기준 문서는 `/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices`와
  실행 모델의 `prompting-claude-<model>` 페이지다.
- `anthropic.com/engineering`, `claude.com/blog` — 엔지니어링 블로그.
- `github.com/anthropics/claude-code` — CHANGELOG와 releases.

공식 호스트는 이전되므로 위 출처에서 시작한 리다이렉트는 따라가되, 검색으로 얻은 링크는 호스트와 조직 경로가
위 목록과 문자 단위로 같은지 확인한 뒤에만 쓴다.
모델 세대가 바뀐 뒤라면 그 세대의 모델 문서와 릴리스 노트를 함께 본다.

1. 가져온 권고의 최신 권장과 어긋나는 설정이 있는가.
   권고가 겨냥한 상황과 판정 대상이 같은 종류일 때만 근거로 쓰고, 발견에는 출처를 함께 적는다.
2. 모델 세대 교체가 무효화한 지시가 남아 있는가 — 모델 지정, 도구·설정 키 이름, 하네스 기본값 전제.

이 환경에서 관찰한 동작과 공식 문서가 보장하는 범위는 구분해 적는다.

### Context health
1. agent·command·skill 본문이 자기 위임 역할보다 절차를 많이 들고 있는가.
2. 오래된 인수인계·임시 메모·실험 기록이 공식 룰처럼 남아 있는가.
3. 설정 총량이 커져 로드 비용이 늘고 있는가. 파일별 분량을 훑고 §룰 파일 2·3의 기준으로 압축 후보를 함께 제시한다.
   총량 판정은 `CLAUDE.md`부터 적용하고, 다른 파일이 들 수 있는 기준이 남아 있으면 §룰 파일 6의 오배치로 낸다.
4. Claude Code 시스템 프롬프트가 이미 강제하는 동작(결론 우선 보고, 전용 도구 사용 등)을
   설정 파일이 같은 방향으로 재진술하는가.
   판정 범위는 그 파일을 읽는 주체로 한정한다 — subagent는 `CLAUDE.md`는 받지만 main의 시스템 프롬프트는 받지 않으므로,
   `CLAUDE.md` 룰은 그것을 실제로 쓰는 agent 소비자를 특정할 수 있으면 하네스 중복이 아니다.

### `README.md` (프로젝트 자체에 대한 설명)
규칙 어긋남 점검은 적용하지 않는다. 대신 다음을 본다.

- 설명이 `CLAUDE.md`·`commands/**`·`skills/**`·`agents/**`의 실제 동작과 일치하는가.
- 폐기되었거나 더 이상 존재하지 않는 기능·구조가 남아 있는가.
- 새로 추가된 기능·파일이 누락되어 있는가.
- 표기·예시·링크가 깨졌는가.

## 출력 형식
- 전체 판정: `정상` / `부족`(역할 프롬프트나 흐름에 구멍) / `과함`(context health 악화) / `충돌`(룰 간 모순).
  해당하는 값을 모두 적는다.
- 역할 프롬프트 판정 (파일별): `충분` / `부분 부족` / `부족`. 기준은 §역할 프롬프트 충분성을 따른다.
- 각 발견에 대해 위치(파일·섹션) + 현재 표현 + 제안 표현(before/after diff).
  위치 오배치는 현재 위치 → 제안 위치 + 옮겨야 할 사유로 적는다.
- 발견은 두 부류로 나눈다.
  `문구` — 표현·중복·위치·일관성만 바뀌고 동작은 그대로인 것.
  사용자가 적용을 요청하면 개별 확인 없이 한 번에 적용하고, 무엇을 고쳤는지 보고한다.
  `동작` — 적용하면 실제 행동이 달라지는 것. diff와 별도로 "적용 후 무엇이 달라지는지"를
  참조 식별자 없는 평문 한두 줄로 함께 적는다. 적용은 사용자의 명시 승인 후에만 한다.
- 우선순위: `동작` 발견 > 소유·위치 오배치 > `문구` 발견. 같은 부류 안에서는 영향 범위가 넓은 것부터 적는다.
- `README.md` 부정확 항목은 별도 묶음으로 분리해 보고한다.
- 다른 파일에도 함께 갱신해야 하는지 명시한다.
- 발견 사항이 없으면 그렇게 말하되, 확인한 파일 범위와 남은 위험을 함께 적는다.

## 제외
- 요청 없는 자동 수정 — 부류별 적용 조건은 §출력 형식을 따른다.
- 지금 실제로 틀렸거나 동작하지 않는 것이 아닌 발견 — 선호나 일반론만 근거로 한 문구 변경, 실제 손해가 없는 참조 부정확이나 중복.
- 아직 일어나지 않은 실패를 막으려고 지침을 더하거나 보강하는 제안.
  그 실패가 이 환경에서 실제로 관찰됐을 때만 낸다.
- 새 워크플로우·정책 체계의 설계 — 감사는 현재 설정의 판정과 그 통합·분리 후보까지다.
- 파일·흐름을 통째로 덜어내자는 제안 — 분량과 구조만으로는 그 경로가 값을 하는지 판정할 수 없으므로,
  실사용 빈도를 사용자에게 확인한 뒤에만 낸다.
